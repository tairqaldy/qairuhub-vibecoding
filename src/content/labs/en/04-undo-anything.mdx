<Lead>
Every approval feels like a *one-way door*. It is not. Break your own project on purpose, three kinds of damage and three ways back, and the door swings both ways.
</Lead>

This is not a git tutorial; commits and branches are [module 09](/en/learn/git-and-github/). It is a nerve tutorial. Anthropic reports that Claude Code users approve 93% of permission prompts, and calls the result "approval fatigue, where people stop paying close attention" ([Anthropic, 25 Mar 2026](https://www.anthropic.com/engineering/claude-code-auto-mode)). You will not read every diff forever, so recovery — not vigilance — is what keeps you safe.

## Three layers, one question

| Layer | Brings back | Leaves alone | Where you type it |
|---|---|---|---|
| Rewind — `Esc` `Esc` or `/rewind` | files Claude's own edit tools changed this session, plus the conversation | anything a Bash command touched, most subagent edits, your own manual edits, anything remote | inside Claude Code, as a menu |
| `git restore` / `git reset --hard` | tracked files, back to your last commit | new untracked files, anything already committed | your terminal |
| `git revert` | a commit already in history, by writing its opposite as a new commit | work you never committed | your terminal |

One question sorts almost every emergency: **did it get committed?** If yes, `git revert`. If no, `git restore` or `git reset --hard`. Still in the same Claude session, with only the edit tools involved? Rewind beats both, and hands your prompt back to reword.

Rewind is a session convenience with an expiry date. Git is the floor you land on. Never let an agent work in a folder git does not know about ([checkpointing](https://code.claude.com/docs/en/checkpointing)).

## Break it three times, bring it back three times

<Steps>

<Step title="Open two windows and make a save point">
Left window: Claude Code. Right window: a plain terminal in the same folder. Keep both open and watch the repo change while the agent works.

<Terminal title="terminal — right window">
```bash
cd qairu-event
git status
git log --oneline
```
</Terminal>

If `git status` shows anything modified, save it now.

<Terminal title="terminal — right window">
```bash
git add -A
git commit -m "save point before lab 04"
```
</Terminal>

The top line of `git log --oneline` is your starting point.

In the left window, start the agent in manual mode:

<Terminal title="terminal — left window">
```bash
claude --permission-mode manual
```
</Terminal>
</Step>

<Step title="Break it on purpose, and let the damage reach a commit">
Give Claude something you do not want, and let it commit. Approve each step.

<Prompt title="Breakage 1 — committed damage" where="Claude Code · manual mode">
```text
Rewrite index.html so that every heading is in ALL CAPITAL LETTERS,
replace the seat counter with the word "SOON", and delete the text
labels on the sign-up form inputs.

Then commit the change with the message "restyle".
```
</Prompt>

Open the page in a browser. It is worse, and the form is now unusable on a screen reader. Good.

<Terminal title="terminal — right window">
```bash
git log --oneline
```
</Terminal>

A new line sits on top: `restyle`. The damage is in your history, which rules out layers two and three.
</Step>

<Step title="Undo #1 — git revert, safe in front of other people">
<Terminal title="terminal — right window">
```bash
git revert --no-edit HEAD
git log --oneline
```
</Terminal>

Reload the browser: the page is back. But `git log` is one line **longer**, not shorter. `git revert` erased nothing: it wrote the bad commit's exact opposite on top.

That is deliberate: rewriting history breaks the clone of anyone who already has that commit, while adding one never does. `--no-edit` skips the text editor. For an older commit, pass its short hash: `git revert --no-edit <hash>`.
</Step>

<Step title="Break it again, without a commit">
<Prompt title="Breakage 2 — uncommitted mess, plus a file you never asked for" where="Claude Code · manual mode">
```text
Change the page background to hot pink, add a giant "SOLD OUT!!!"
banner above the form, and create a new file called scratch-notes.md
with your reasoning.

Do not commit anything.
```
</Prompt>

Approve it. Now two problems sit in one folder: a modified tracked file, and a brand-new file git has never seen. They need different commands.

<Terminal title="terminal — right window">
```bash
git status
git diff --stat
```
</Terminal>

`index.html` sits under "Changes not staged for commit". `scratch-notes.md` sits under "Untracked files".
</Step>

<Step title="Undo #2 — throw the uncommitted mess away">
<Terminal title="terminal — right window">
```bash
git restore .
git status
```
</Terminal>

`index.html` is clean. `scratch-notes.md` is still there: `git restore` only restores files git already tracks.

For untracked leftovers, look before you shoot: `-n` prints what would go and deletes nothing.

<Terminal title="terminal — right window">
```bash
git clean -nd
```
</Terminal>

<Callout type="danger" title="git clean is the one command in this lab with no undo">
`git clean -fd` deletes untracked files permanently. Git never had a copy, so no revert, no reset and no rewind brings them back. Read the `-nd` list first, every time. Files in `.gitignore` are left alone — unless you add `-x`, which you should not do while learning.
</Callout>

`scratch-notes.md` should be the only line on that list. Now delete it for real — `-f` does it.

<Terminal title="terminal — right window">
```bash
git clean -fd
git status
```
</Terminal>

One case defeats `git restore`: if `git add` already ran, the bad change sits in staging and `git restore .` copies it back into your files. The hammer for that is `git reset --hard` — every tracked file, staged and unstaged, back to your last commit. Run it now; your tree is clean, so it costs nothing.

<Terminal title="terminal — right window">
```bash
git reset --hard HEAD
git status
```
</Terminal>

<Callout type="warn" title="Why the agent will not do this one for you">
In auto mode, Claude Code's classifier blocks `git reset --hard`-style discards of uncommitted work, and force pushes, by default ([permission modes](https://code.claude.com/docs/en/permission-modes)). Commands that destroy work you cannot get back, you type yourself.
</Callout>
</Step>

<Step title="Undo #3 — rewind, without touching git at all">
Before any undo, the cheapest move: press `Esc` **once** while Claude is mid-answer. It stops and keeps the work already done — half a wrong change is easier to fix than a whole one.

Now break the page a third time and take it back from inside the session.

<Prompt title="Breakage 3 — pure edit-tool damage" where="Claude Code · manual mode">
```text
Rename every CSS class in index.html to a single letter to save bytes.
Do not commit.
```
</Prompt>

Approve it, then look at what it did to a file you have to maintain. With an **empty input box**, press `Esc` twice (or `/rewind`).

A menu lists your prompts; each prompt that starts a turn makes a checkpoint. Six choices: Restore code and conversation, Restore conversation, Restore code, Summarize from here, Summarize up to here, Never mind.

Pick the CSS-renaming prompt and choose **Restore code and conversation**. The file goes back and the prompt returns to your input box, ready to reword. Check from the outside:

<Terminal title="terminal — right window">
```bash
git status
```
</Terminal>

Nothing modified. You just undid an agent's work without a single git command.

<Deeper title="Try an idea without losing the session you are in">
Rewind moves you backwards along one line. To try an alternative and keep the original conversation, the docs point at `/branch` or `claude --continue --fork-session`: same history behind you, two futures in front ([checkpointing](https://code.claude.com/docs/en/checkpointing)).
</Deeper>
</Step>

<Step title="Find the undo that does not exist">
The most important step in this lab. It takes ninety seconds.

<Prompt title="The side effect" where="Claude Code · manual mode">
```text
Using a shell command, not your edit tool, create a file called
agent-was-here.txt containing today's date. Then stop.
```
</Prompt>

Approve the Bash call. (If Claude reaches for its edit tool anyway, reply: `run it as a shell command, not with your edit tool`.)

Press `Esc` `Esc` and restore the code to before that prompt. Then look in the right window:

<Terminal title="terminal — right window">
```bash
git status
```
</Terminal>

`agent-was-here.txt` is still there. Rewind restored nothing: checkpoints snapshot what Claude's *edit tools* touch, and a Bash command is not an edit tool.

Clean it up yourself. Dry run first:

<Terminal title="terminal — right window">
```bash
git clean -nd
```
</Terminal>

One file on the list, the one you expected. Now for real.

<Terminal title="terminal — right window">
```bash
git clean -fd
```
</Terminal>
</Step>

<Step title="Finish clean, then write the rule down">
<Terminal title="terminal — right window">
```bash
git status
git log --oneline
```
</Terminal>

A clean working tree. Above your starting point, two lines: the breakage and the revert that cancelled it. Everything else you did today left no trace.

Now turn it into a standing rule, in the memory file from [lab 03](/en/labs/claude-md-and-permissions/):

<Prompt title="Teach it the habit" where="Claude Code · any mode">
```text
Add this to CLAUDE.md, in the existing rules section, in one line:
before starting any change that touches more than two files, stop and
tell me to commit first.
```
</Prompt>

Approve the edit and commit CLAUDE.md. Next week the agent reminds you, not the other way round.
</Step>

</Steps>

## The damage that has no undo

Three layers cover your files. Nothing beyond them.

<Callout type="danger" title="Nothing in this lab reverses any of these">
A `git push` other people have already pulled. A deploy that is live. A row deleted from a database. A message that was sent. A file removed by a Bash `rm`. A charge on a paid API. An API key that reached a public repo — that key is burned, and rotating it is the only fix.

The rule is not "review everything". It is: know which actions leave your machine, and slow down for those.
</Callout>

<Deeper title="You reset too far and lost a commit. Try git reflog.">
`git reflog` prints every position your branch tip has held recently, including ones you just threw away. Find the line from before the mistake, copy its hash, then `git reset --hard <hash>` to go back — or `git checkout -b rescue <hash>` to look first.

The limit is exact: reflog only knows commits. Work that was never committed was never written down, so nothing finds it.
</Deeper>

## Lock it in

<Prompt title="Panic prompt" where="Claude Code · paste this when you have already broken something">
```text
I need to undo something. Do not change any files yet.

1. Run `git status` and `git log --oneline -5` and show me the raw output.
2. Tell me which of these describes my situation:
   (a) the bad change is already committed
   (b) the bad change is uncommitted
   (c) both, plus new files I never asked for
3. For my case, give me the exact commands in the order I should run them,
   and for each one say what it deletes permanently.
4. Tell me what git cannot recover here, if anything.

Then stop and wait. I will run the commands myself.
```
</Prompt>

Save that one. The agent explains the recovery, you type the commands — the right split for anything destructive.
