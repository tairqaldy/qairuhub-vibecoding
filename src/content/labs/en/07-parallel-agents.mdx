<Lead>
A git worktree is a second folder of the same repository, on its own branch. Two agents can then edit *at the same time* and never see each other's files. The merge tells you whether that was a good idea.
</Lead>

## Look at the bill before you open a second terminal

Parallelism is not a speed setting. Anthropic's January 2026 guidance puts a multi-agent setup at [three to ten times the tokens of one agent](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) for the same task, and says to try single-agent options first. Its earlier research system measured [about fifteen times the tokens of chat](https://www.anthropic.com/engineering/multi-agent-research-system); coding has fewer parallel parts than research.

<StatRow>
  <Stat value="3–10x" label="tokens of one agent, same task" source="Anthropic, 23 Jan 2026" href="https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them" tone="warn" />
  <Stat value="16" label="parallel Claudes that built a C compiler" source="Anthropic, 5 Feb 2026" href="https://www.anthropic.com/engineering/building-c-compiler" tone="info" />
  <Stat value="~$20,000" label="API cost of that two-week run" source="Anthropic, 5 Feb 2026" href="https://www.anthropic.com/engineering/building-c-compiler" tone="warn" />
</StatRow>

That C compiler is the ceiling: sixteen instances, roughly 2,000 sessions, about 100,000 lines of Rust. It worked because the test suite was near-perfect. Without an automated check, parallel agents just multiply unverified code.

<Compare a="Two agents are just expensive" b="Two agents earn their keep">
<div slot="a">
Anything sequential. Anything where both halves depend on one design decision. Anything a better prompt or a `/clear` would have fixed. Anything you cannot test automatically.
</div>
<div slot="b">
Two features that touch different files. A build plus a separate review with fresh eyes. Work you can test half at a time, in a browser.
</div>
</Compare>

<Callout type="warn" title="The pushed-work trap">
By default `--worktree` branches from the remote default branch, not from what you have locally. Commit without pushing and both agents start from old code. Push first; the Deeper box has the alternative.
</Callout>

## Run both agents, then merge them

<Steps>

<Step title="Pick two features that do not share a decision">
For QAIRU Event Sign-up: a **dark mode toggle**, and a **seats-left counter** that disables the form when the event is full. One is presentation, one is logic.

Write each as one sentence first. If you cannot, it is one task, not two. Stay in a single session.
</Step>

<Step title="Clear the deck">
In the main folder:

<Terminal title="bash">
```bash
git status
git log --oneline
```
</Terminal>

Status must be clean. Three copies of this repo are about to exist on disk; do not lose track of which holds uncommitted work.
</Step>

<Step title="Terminal A — start the first agent in its own worktree">
<Terminal title="bash">
```bash
claude --worktree dark-mode
```
</Terminal>

That one flag does the whole setup: a new folder at `.claude/worktrees/dark-mode/`, on a new branch `worktree-dark-mode`. You never run `git worktree add` yourself. Give it a scoped prompt:

<Prompt title="Agent A" where="Claude Code · worktree dark-mode">
```text
Add a dark mode toggle to the sign-up page.

Scope — you may edit ONLY these files:
  index.html, styles.css
Do not touch CLAUDE.md, README.md, or anything under .github/.

Requirements:
- A visible toggle in the header.
- The choice is remembered in localStorage and applied before first paint.
- Form labels and the submit button stay readable in both themes.

Follow CLAUDE.md. When it works, commit on this branch with a one-line message.
Then stop and tell me what you changed, file by file.
```
</Prompt>
</Step>

<Step title="Terminal B — start the second agent from the same main folder">
Open a second terminal in the **same** project folder — not inside the first worktree.

<Terminal title="bash">
```bash
claude --worktree seats-left
```
</Terminal>

<Prompt title="Agent B" where="Claude Code · worktree seats-left">
```text
Add a seats-left counter to the sign-up page.

Scope — you may edit ONLY these files:
  index.html, seats.js
Do not touch styles.css, CLAUDE.md, or README.md.

Requirements:
- Show "N seats left" next to the form, read from one capacity constant.
- When N reaches 0, disable the submit button and show a short "full" message.
- All logic lives in seats.js. index.html gets one script tag and one container div.

Follow CLAUDE.md. When it works, commit on this branch with a one-line message.
Then stop and tell me what you changed, file by file.
```
</Prompt>

Both prompts name the files. That is the most useful line here.
</Step>

<Step title="Terminal C — watch from outside while they work">
<Terminal title="bash">
```bash
git worktree list
```
</Terminal>

Three entries: your main checkout and the two worktrees. Open each worktree's `index.html` in a browser and test it now, while the agents still run — each half checked before it meets the other.

If your project has dependencies, run your install command inside each worktree. A worktree is a fresh checkout; `node_modules` does not travel.
</Step>

<Step title="Review each branch with a context that did not write it">
After agent A commits, in Terminal A:

<Prompt title="Fresh-eyes review" where="Claude Code · either worktree, after the commit">
```text
Use a subagent to review this branch's diff against the main branch.
Report only correctness problems and violations of CLAUDE.md — not style, not naming.
For each finding give me: the file, what breaks, and the smallest fix.
If you find nothing real, say so and stop.
```
</Prompt>

A subagent gets its own context window, so it is not attached to code it just wrote — [the best-practices page](https://code.claude.com/docs/en/best-practices) recommends this split. Fix what is real, repeat in Terminal B.
</Step>

<Step title="Exit both sessions and keep the worktrees">
Leave each session. A worktree with no changes is removed on exit; one with commits asks whether to keep it. **Choose keep** — you need those branches.
</Step>

<Step title="Merge the first branch">
Back in the main folder:

<Terminal title="bash">
```bash
git merge worktree-dark-mode
```
</Terminal>

This one lands clean: nothing on main has moved since the branch started.
</Step>

<Step title="Merge the second branch and meet the conflict">
<Terminal title="bash">
```bash
git merge worktree-seats-left
```
</Terminal>

Both agents edited `index.html`. When their edits land in the same region, git stops and leaves conflict markers. Expected, not a mistake. Hand it to an agent in the main folder:

<Prompt title="Conflict resolution" where="Claude Code · main folder, mid-merge">
```text
git merge left conflict markers in index.html.
Resolve them so BOTH features survive: the dark mode toggle and the seats-left counter.
Do not delete either feature to make the conflict go away.
When the file is clean, show me the resolved section, then give me the exact steps
to test both features in the browser before I commit the merge.
```
</Prompt>

Read the resolved section before you commit. An agent resolving a conflict is guessing at intent, and the cheapest way to lose a feature is a resolution that dropped half of it.

If git merges both edits without complaining, you got lucky with line numbers. Open the page anyway: a clean merge is not a working page.
</Step>

<Step title="Verify on main, then clean up">
Open the page from the main folder. Toggle the theme; the seats counter must still update.

<Terminal title="bash">
```bash
git worktree remove .claude/worktrees/dark-mode
git worktree remove .claude/worktrees/seats-left
git branch -d worktree-dark-mode worktree-seats-left
git worktree list
```
</Terminal>

Remove the worktrees before deleting the branches — git refuses to delete a branch that is still checked out somewhere.

Optional finish, from a normal shell:

<Terminal title="bash">
```bash
claude -p "Summarize what changed in the last 3 commits in 5 bullets" \
  --allowedTools "Bash(git log *),Bash(git diff *)" --output-format json
```
</Terminal>

Find `result`, `session_id` and `total_cost_usd` in the JSON. That last field is the point of this lab. `--allowedTools` is not decoration: `-p` starts in Manual mode, so an unallowed command is denied outright — and the summary gets written without ever reading the log.
</Step>

</Steps>

## The conflict was the lesson, not the accident

Worktrees isolate **files**, not **decisions**. Both agents wrote good code for `index.html` and still collided: neither knew the other was rearranging the same header. Claude Code enforces the file half — a worktree session blocks edits, commands and git redirects aimed at the main checkout. The decision half is yours.

The skill is not typing `--worktree`. It is splitting work along file lines before anything starts:

- **One owner per file.** As in both prompts above.
- **Give the second agent its own file.** `seats.js` exists so only one line of `index.html` has to change.
- **Never let two agents edit CLAUDE.md, the README or config** in one run.
- **Merge the same day.** A stale branch turns a small conflict into an afternoon.

## When two agents is an expensive way to get one result

[Cognition's June 2025 argument](https://cognition.com/blog/dont-build-multi-agents) against multi-agent systems holds where it matters: every action carries an implicit decision, and conflicting decisions produce bad results. That is your `index.html` conflict, scaled up.

The default that survives real work is modest: one agent, subagents for research, a fresh context to review. [Module 14](/en/learn/multi-agent/) makes the case.

<Deeper title="Where the branch actually starts from, and how to bring your .env along">
By default worktrees use `worktree.baseRef: "fresh"`: they branch from the remote default branch (`origin/HEAD`), falling back to local HEAD when there is no remote. For unpushed work, set `{"worktree": {"baseRef": "head"}}` in your Claude Code settings.

A fresh checkout carries no ignored files and no dependencies. List the ignored files you need — `.env`, for example — in a `.worktreeinclude` file, gitignore syntax, and they are copied into each worktree. Dependencies you reinstall. Source: [the worktrees docs](https://code.claude.com/docs/en/worktrees).
</Deeper>

<Deeper title="The manual route, which works in any tool">
`--worktree` is Claude Code's wrapper around plain git, so the same isolation works with Cursor, Codex, Gemini CLI or a bare editor:

<Terminal title="bash">
```bash
git worktree add ../qairu-dark-mode -b dark-mode
git worktree list
git worktree remove ../qairu-dark-mode
```
</Terminal>

Then `cd` in and start whichever agent you like.
</Deeper>

<Deeper title="Bigger than two: /batch, agent teams and workflows">
`/batch` plus one instruction splits a large change across 5–30 worktree-isolated subagents, each opening its own pull request. Agent teams — a lead plus teammates on one task list — are experimental, off by default, and not worktree-isolated, so you partition files by hand; the costs page puts them at roughly seven times a standard session's tokens in plan mode. Dynamic workflows run up to 16 concurrent agents. Read [the agents overview](https://code.claude.com/docs/en/agents) first: all three multiply the bill you just measured.
</Deeper>
