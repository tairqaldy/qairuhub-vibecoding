<Lead>
You already have the idea. It lives in your head as a *feeling*, and an agent cannot read feelings. It reads text. Everything you leave out, it fills in for you — confidently, in code, in about ninety seconds.

One page of writing and one prompt. It is the cheapest work in the course, because every mistake here gets multiplied by every line the agent writes afterwards.

## The agent builds what you wrote, not what you meant

Ask for "a sign-up page for our event" and you will get one. You will also get a login form nobody asked for, a phone-number field you did not want, an invented event with an invented date, and a save button that writes to a variable which disappears when the tab closes. None of that is a malfunction. Each one is a decision you did not make, so the model made it for you.

[Module 03](/en/learn/problem-solving-mindset/) gave you the habit: decide before you prompt. This module gives you the file. A decision in your head is one the agent cannot read. One you typed into a chat three sessions ago is gone. One page, on disk, at the start of every build.

## Five questions that fit on one page

PRD stands for product requirements document. Ignore the corporate name. Here it is one page, five answers, written before anything exists and saved as `PRD.md` next to your code. Some tools call the same file `SPEC.md`. Pick one name and use it everywhere.

**Problem.** One sentence about the pain, not the feature. "Seats fill up in a Telegram thread and nobody knows who is actually coming" is a problem. "We need a sign-up form" is a solution that smuggles in decisions you have not examined.

**User.** Specific enough to picture one person. A student in Astana, on a phone, on mobile data, deciding right now whether she has a seat. Her constraints — small screen, slow connection, no patience — are requirements in disguise.

**The one job.** People do not want your product. They hire it to get a job done, and fire it when something does that job faster. Your user is not hiring a sign-up page. She is hiring certainty that she has a seat. Write that job as one sentence in her words. If it contains "and", you have two jobs: keep the one that hurts more.

**Definition of done.** One or two sentences a stranger or a script could run to prove it works. The hardest of the five — its own section is below.

**Not building.** What you are deliberately leaving out.

## The not-building list is the part that pays

Every line in it is a decision the agent no longer gets to make for you. It is also the only part of a PRD that gets shorter as you improve.

A first build you can finish in one sitting: one page, no login, no payments, no admin panel, data in the browser or one file, deployed by dragging a folder. Everything else is version two. If the plan comes back bigger than you expected, cut the must-have list in half and ask again.

<Callout type="warn" title="Some things are out of scope for a different reason">
Do not let an agent invent your login, your database permissions or your payment flow while you are learning. A scan of 1,645 Lovable-built apps found 170 that let anyone read user names, email addresses, financial information and secret API keys ([Semafor, 29 May 2025](https://www.semafor.com/article/05/29/2025/the-hottest-new-vibe-coding-startup-lovable-is-a-sitting-duck-for-hackers)). When you genuinely need accounts, use a managed service and have a human read that part ([module 11](/en/learn/security/)). For a first build, "no accounts" is a security decision, not a limitation.
</Callout>

## Write "done" in words a stranger could act on

**Weak.** The sign-up should feel fast and look clean. An agent will cheerfully claim both, and you have nothing to argue with.

**Strong.** A person who has never seen the page opens the link on a phone, types a name and an email, presses one button, and sees a confirmation. You open the list and the name is there. Two people signing up in the same second do not overwrite each other.

Three sentences, no adjectives, each one a thing somebody can do in front of you. Notice the last one: nobody writes that clause, and everybody ships that bug. [Anthropic's Claude Code guide](https://code.claude.com/docs/en/best-practices) describes a good spec the same way — self-contained, naming the files involved, stating what is out of scope, giving one end-to-end verification step.

## Hand it over: read, ask, plan, do not code

<Prompt title="Hand the PRD to the agent" where="Claude Code · plan mode">
```text
Read PRD.md. Do not write any code yet.

1. Tell me back, in five lines, what you understood: the problem, the user,
   the one job, my definition of done, and what is out of scope.
2. Ask me exactly 3 questions — the three points in the PRD where guessing
   wrong would cost the most. One at a time.
3. After I answer, write PLAN.md:
   - ordered steps, each small enough to verify on its own
   - the files each step creates or changes
   - the check that proves that step works
   - what you will NOT touch
   - any assumption you are making that I should confirm

Stop there and wait for my approval. If a step turns out to be wrong while you
are implementing it, stop and update the plan instead of improvising.
```
</Prompt>

Three questions, not "any questions". A hard limit forces the agent to rank, and the three it picks show you which parts of your page are thin. You run this prompt for real in [module 07](/en/learn/the-agent/).

## Spec-driven development is a dial, not a religion

Turn this one page into a whole toolchain and you have spec-driven development. GitHub's Spec Kit is the best-known version: open source under MIT, Python 3.11 or newer, installed with `uv tool install specify-cli` and started with `specify init my-project --integration copilot`. Its commands run in order: `/speckit-constitution` for project principles, `/speckit-specify` for what and why, `/speckit-plan` for the technical approach, `/speckit-tasks` for work items, `/speckit-implement` to build, `/speckit-converge` to re-check progress against the spec. Implement and converge repeat until it reports that it has converged ([github.com/github/spec-kit](https://github.com/github/spec-kit)). It moves fast: seven releases landed between 1 and 21 September 2026. Read the README, not last year's tutorial.

You do not need any of it today. Testing these toolkits, Birgitta Böckeler found the elaborate process created a false sense of control: the agent still skipped some instructions and over-applied others ([martinfowler.com, 15 Oct 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). More markdown is not more certainty. One page you reread beats six templates you skimmed.

<Deeper title="Three different things people mean by 'spec-driven'">
Böckeler separates them. **Spec-first**: you write the spec, the agent builds, and afterwards the code is the truth. **Spec-anchored**: the spec stays alive, and every change goes through it before it reaches the code. **Spec-as-source**: humans edit only the spec, and the generated code is marked do-not-edit. All three get called the same name, which is why people argue past each other.

Two other toolkits, for when you go looking: AWS Kiro splits a spec into `requirements.md`, `design.md` and `tasks.md` with approval gates between the phases ([kiro.dev/docs/specs](https://kiro.dev/docs/specs/)); BMAD now ships as skills and plugins around a Clarify → Plan → Build and verify → Learn and adjust loop ([github.com/bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)).
</Deeper>

  myth="Writing things down like this only works for prototypes."

In February 2026 Anthropic published a C compiler written almost entirely by agents: 16 parallel Claude instances, roughly 2,000 sessions over two weeks, about $20,000 of API cost, and around 100,000 lines of Rust that compiles Linux 6.9 on x86, ARM and RISC-V. What made it possible was not a bigger model but a definition of done the agents could run themselves: the compiler test suites. An agent solves exactly the problem the tests define, so weak tests produce the wrong product. Precision scales. Vagueness does not.
</Myth>
