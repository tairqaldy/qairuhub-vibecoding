<Lead>
An agent can write a thousand lines while you finish your coffee. It builds *the wrong thing* just as fast, and it will not stop to tell you. Everything hard about building software lives in that gap.
</Lead>

## The bottleneck moved

The slow part of building software used to be the code itself. Simon Willison's guide for coding agents has a chapter titled "writing code is cheap now" ([Agentic Engineering Patterns](https://simonwillison.net/guides/agentic-engineering-patterns/)).

The cost did not disappear. It moved to knowing exactly what to ask for, and to noticing when the answer is wrong.

<StatRow>
  <Stat value="66%" label="complain about AI output that is almost right, but not quite" source="Stack Overflow Developer Survey 2025" href="https://survey.stackoverflow.co/2025/ai" tone="warn" />
  <Stat value="33%" label="say they trust the accuracy of what it produces" source="Stack Overflow Developer Survey 2025" href="https://survey.stackoverflow.co/2025/ai" tone="info" />
</StatRow>

"Almost right" is the failure of this era. Code that does not run is easy: the machine tells you. Code that runs and quietly adds the tip to the wrong person is caught by a human or by nobody. The scarce skill is specification and judgement, not typing speed.

## Four steps, only one of them typing

The mathematician George Pólya split problem-solving into four steps: understand the problem, devise a plan, carry out the plan, look back. He meant mathematics. It transfers anyway, because the agent only ever does step three.

| Pólya | With an agent | Who does it |
|---|---|---|
| Understand the problem | Say who it is for, the one job it does, and what is out of scope | You |
| Devise a plan | Plan mode: it proposes files and steps, you read and edit them | Both |
| Carry out the plan | It writes the code, runs the commands, shows the diff | It |
| Look back | Run the check, read the evidence, decide if this is what you meant | You |

Anthropic's Claude Code guide arranges the work the same way — explore, plan, code, commit ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Three of the four steps are thinking.

<Callout type="live" title="On stage">
Ask someone who has never written code for a one-sentence app idea. Write it on the board word for word. Ask three people what they pictured. Three different apps out of one sentence — the whole module in ninety seconds.
</Callout>

## A vague idea is not a specification

The difference is not length. It is decisions. A vague idea leaves every one of them to the model, and the model decides confidently.

<Compare a="The idea, as you say it out loud" b="The same idea, as a specification">
<div slot="a">

**"An app to split the bill at a cafe."**

Split evenly, or by what each person ate? Which currency? Does it round? If it rounds, do the rounded amounts still add up, or is the waiter short 30 ₸? Is there a service charge? Who types it in — one person or everyone? Does it need an account? Does it work offline?

Eight decisions, none of them made. The agent makes all eight and never mentions it.

</div>
<div slot="b">

**Dastarkhan Split** — splits a cafe bill between friends in tenge.

**User and job.** Four friends, one phone, one minute before the waiter comes back.

**Must have.** Add people by name. Add items with a price and tick who shared each one. A service charge field, default 10%. Each person's share rounded to the nearest 10 ₸ — and the rounded shares still add up to the exact total. A "Copy summary" button that produces plain text for Telegram.

**Out of scope.** Accounts, payments, saved history, anything that needs the internet.

**Constraints.** One HTML file, no libraries, usable on a 360px phone, English with a Kazakh toggle.

**Done when.** A 3-person, 4-item bill matches a hand calculation. The rounded shares sum exactly to the total. Negative and empty prices are refused. The link opens on a phone.

</div>
</Compare>

The right-hand column is not more technical: no framework, no function, no file name in it. It is longer because every sentence is a decision you made instead of left. That is what separates a specification from a wish.

A spec this size builds in one go. A bigger one does not. Cut the must-have list into pieces that each finish and get checked alone — "add people and items" is one, "rounding that still sums to the total" is another. Start with the riskiest piece, not the easiest. If you cannot name a piece's check, it is two pieces.

<Callout type="warn" title="Specs have a cost, so size them">
Do not write this for a typo. [Anthropic's guide](https://code.claude.com/docs/en/best-practices) draws the line at one sentence: if you can describe the change in a sentence, just make it. Birgitta Böckeler found one spec toolkit far too heavy for a small bug, and another's generated markdown more tedious to review than code ([martinfowler.com, 15 Oct 2025](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). One-line change: no spec. Feature across several files: spec. Multi-week product: spec plus a plan on disk ([module 04](/en/learn/idea-to-prd/)).
</Callout>

## Explaining the problem is half of solving it

Programmers have an old habit: describe the bug out loud to a rubber duck on your desk. Halfway through the sentence you hear the answer. The duck does nothing — forming the sentence does everything.

An agent is a rubber duck that asks follow-up questions. Use it that way before you use it as a typist: give it the idea, forbid code until it has interviewed you. The interview often ends with you realising the feature you wanted is not the one you needed — four minutes instead of four hours.

For anything bigger than a small change the Claude Code docs recommend: one line in, an interview, a spec on disk, a fresh session to build from it ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

<Prompt title="Idea → spec, with an interview" where="Claude Code · plan mode · or any chat window">

```text
Here is my idea: [one or two sentences].

Do not write any code yet. First, interview me. Ask one question at a time,
and skip anything you can already work out for yourself. Dig into the parts
I have probably not thought through:
- who this is for, and the single job they need done
- the smallest version that is still useful, and what is explicitly out of scope
- the unhappy paths: empty, wrong, too large, duplicated, offline
- constraints you must respect: [stack / device / language / budget / deadline]
- how we will both know it works — checks a person or a script can run

When you have enough, stop asking and write SPEC.md with these sections:
problem and user; must-have list; out of scope; constraints; three example
inputs with the exact output I should see; and a "done when" list of checks.

Then tell me the three assumptions in that spec most likely to be wrong,
and what you would have to know to settle each one.
```

</Prompt>

That last paragraph is the easiest one to cut. Keep it. An agent asked to attack its own spec is worth far more than one asked to praise it.

<Deeper title="Why an hour spent on the question is never wasted">
Dex Horthy of HumanLayer describes how a mistake multiplies: one bad line of research becomes many bad lines of plan, and one bad line of plan becomes hundreds of bad lines of code ([Advanced Context Engineering for Coding Agents](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)).

So the cheapest thing to review is the research, then the plan, then — last and worst — the diff. Most people do it backwards: approve everything, then read two thousand lines they do not understand. Review the 200-line plan instead. Same information, before it multiplied.
</Deeper>

## "Done" has to be something a machine can check

"Make it work" is not a definition of done. "Make it look nice" is worse. Without a runnable check, the agent stops when the work *looks* finished — and you become the test suite.

Write the check into the request. Three tests that must pass. A command that must exit cleanly. A number you worked out by hand that the screen must match. Claude Code's `/goal` command re-checks a condition after every turn; phrase it so the agent's own output proves it — `npm test` exiting 0, `git status` coming back clean ([/goal docs](https://code.claude.com/docs/en/goal)).

Ask for evidence, not a verdict. "Tests pass" is a claim; the command and its output pasted back is a fact. Agents grade their own work too generously, which is why Anthropic's long-running setups give the evaluator a separate role from the generator ([Harness design for long-running apps, 24 Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)).

## How to disagree with an agent

It will be wrong, confidently, in front of you. Kent Beck lists three signals to take the wheel back: it loops, it adds functionality nobody asked for, and it cheats — disabling or deleting tests to get a green result ([Augmented Coding, 25 Jun 2025](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)).

Disagreeing well is a technique, not a mood:

- **Bring evidence, not adjectives.** "This is wrong" gives it nothing. "I ran `npm test`, here is the output, line 14 expected 2 and got 11" gives it the whole problem.
- **Say what you expected and what you saw.** Two sentences. Most bad agent output is a correct answer to a question you did not ask.
- **Ask it to explain before it edits.** "Explain in three sentences why this happens, then wait." If the explanation is nonsense, the fix would have been too.

## When to stop prompting and start thinking

There is a specific feeling: you are typing the fourth variation of the same request, faster and in capital letters. That feeling means the problem is no longer in the prompt.

Stop when any of these are true:

- You have corrected the same thing twice. Clear the session and rewrite the request from scratch.
- You cannot say in one sentence what would make you accept the answer.
- You are reading a diff you do not understand and are about to approve it anyway.
- The thing you are rescuing has been broken longer than a smaller rebuild would take. Instructors at a beginners' vibe-coding class say the same: build several small things instead of rescuing one broken one ([report, Mar 2026](https://www.aol.com/news/joined-vibe-coding-workshop-learn-040201765.html)).

None of these is a failure of the tool. They are the four moments where the work is thinking.
