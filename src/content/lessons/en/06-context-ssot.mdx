<Lead>
Your agent starts every session knowing how to program and nothing about your project. Not the test command. Not the rule you explained three times yesterday. There is one file that fixes this, and *almost everyone* overfills it.
</Lead>

Claude Code's guide names "over-specified CLAUDE.md" as one of its five common failure patterns. Bloat makes the agent ignore rules that are sitting right there in the file. The file that changes behaviour most is the short one, and the docs set the target at under 200 lines. ([best practices](https://code.claude.com/docs/en/best-practices), [memory](https://code.claude.com/docs/en/memory))

## Context is a budget you spend, not a container you fill

In September 2025 Anthropic named the discipline. Context engineering is choosing which tokens occupy the window when the model answers. The window is finite ([module 02](/en/learn/ai-in-plain-language/)), and recall drops as it fills — the effect the post calls context rot. ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents))

So your memory file is not a folder of documentation. It is a standing charge, paid again in every session — including the ones about a file it has nothing to do with.

The post also sets the target for how a standing rule should read: the "right altitude". Specific enough to steer the model, general enough to work as a heuristic. Not brittle if-else rules. Not "write good code". At the right altitude a rule sounds like this: all database access goes through `src/lib/db`, with no Supabase calls inside components.

Prompt engineering was about the sentence you type. Once an agent runs in a loop, your sentence is a small fraction of what the model sees: the files it read, the command output it dumped in, and what your memory file is still charging you for. A perfect prompt in a polluted window loses to an ordinary prompt in a clean one.

## What belongs in the file, and what poisons it

The docs give an include list and an exclude list. Most bad memory files are made entirely of the second one.

<Compare a="What people write" b="What changes behaviour">
<div slot="a">

- A tour of every folder in the repo
- Long pasted API documentation
- "Write clean, maintainable code"
- Language conventions the model already knows
- Anything readable from the code
- Fast-changing facts (the current sprint, today's bug)

</div>
<div slot="b">

- Commands the agent cannot guess: install, dev server, typecheck, **how to run one test file**
- Style rules that differ from the defaults
- Repo etiquette: branch names, never push to `main`, PR expectations
- Architecture decisions specific to this project
- Gotchas that have already bitten someone
- Pointers — file paths and links — not pasted content

</div>
</Compare>

Two rules keep it short. Add a line when the agent makes the same mistake twice. Cut a line when removing it would not cause a mistake. `/doctor` proposes the cuts for a file you have already committed, and emphasis words like IMPORTANT only work when one or two lines carry them. ([memory](https://code.claude.com/docs/en/memory), [best practices](https://code.claude.com/docs/en/best-practices))

Three things never go in:

**Secrets.** The project file is committed. Put the shape of your config in it (`.env.local` is required, see `.env.example`) and never a value. A `Read(./.env)` deny rule helps, but the docs are blunt: it is convenience, not a security boundary. It covers `cat` and `head` in Bash, not a script that opens the file itself. ([permissions](https://code.claude.com/docs/en/permissions))

**A style manifesto.** Platitudes are on the official exclude list: "write clean code" gives the model no decision it could not already make.

**"Read all the docs before starting."** The post calls the alternative just-in-time retrieval: keep light identifiers — paths, queries, links — and let the agent load the data when it needs it. Claude Code already works this way: grep and glob, not an index built up front. Hand it addresses, not cargo.

## CLAUDE.md, AGENTS.md, and which one your tool reads

`AGENTS.md` is the open-standard version of the same idea: plain Markdown, no required fields, a predictable place for commands, style, security notes and PR rules. Its site calls it a "README for agents". ([agents.md](https://agents.md/))

It is no longer one company's format. On 9 December 2025 the Linux Foundation announced the Agentic AI Foundation, with three founding projects: MCP from Anthropic, goose from Block, and AGENTS.md from OpenAI. Platinum members include AWS, Anthropic, Block, Bloomberg, Cloudflare, Google, Microsoft and OpenAI. Today the file is read by Codex, Cursor, GitHub Copilot, Aider, Zed, VS Code, JetBrains Junie, Jules, Warp, Devin and more.

Claude Code reads it too, with one rule. Since v2.1.277 it reads `AGENTS.md` natively **when there is no CLAUDE.md** in or above the working directory. If a `CLAUDE.md` exists, only `CLAUDE.md` is read, unless you set project instructions to `claude-md-and-agents-md`. In some sessions — Bedrock, or telemetry disabled — native reading is not available at all. ([memory#agents-md](https://code.claude.com/docs/en/memory#agents-md))

The portable move, the one that survives a change of tool or version: make `AGENTS.md` the single source of truth and put one line in `CLAUDE.md`:

```markdown
@AGENTS.md
```

Now every tool reads the same file, and there is one file to keep honest.

<Deeper title="Monorepos, Codex paths, and scoped rules">
In a monorepo the nearest `AGENTS.md` to the edited file wins, and an explicit instruction in chat overrides any file. OpenAI's own main repo is cited as carrying 88 of them.

Codex reads a global `~/.codex/AGENTS.md`, then every directory from the git root down to your current one, with a combined cap set by `project_doc_max_bytes` (32 KiB by default). ([Codex agent configuration](https://learn.chatgpt.com/docs/agent-configuration/agents-md))

Claude Code has the matching trick: subdirectory `CLAUDE.md` files load on demand when Claude reads files there, and `.claude/rules/*.md` with a `paths:` frontmatter load only when a matching file is touched. That is how a rule about migrations costs nothing on a CSS task.
</Deeper>

## Where the file lives decides who it binds

The same file name exists at four levels. Pick the wrong one and a good rule ends up stuck on your laptop, or pushed onto every project you open.

| Scope | Where it lives | Who it binds |
|---|---|---|
| Managed policy | `C:\Program Files\ClaudeCode\CLAUDE.md` (Windows), `/etc/claude-code/CLAUDE.md` (Linux/WSL), `/Library/Application Support/ClaudeCode/CLAUDE.md` (macOS) | everyone in the organisation — set centrally, not by a repo |
| User | `~/.claude/CLAUDE.md` | you, in every project you open |
| Project | `./CLAUDE.md` or `./.claude/CLAUDE.md` | everyone who clones the repo — commit it |
| Local | `./CLAUDE.local.md` | you, in this project only — add it to `.gitignore` |

A second memory system runs beside yours. Claude keeps its own notes in `~/.claude/projects/<project>/memory/`, and loads the first 200 lines or 25 KB of `MEMORY.md` each session. "Remember that I prefer short answers" writes there; "add this to CLAUDE.md" writes to your file. Use `/init` for a starter, `/memory` to edit, `/context` to confirm what loaded. ([memory](https://code.claude.com/docs/en/memory))

## A memory file is not a PRD

A PRD ([module 04](/en/learn/idea-to-prd/)) answers one question once: what we are building and what "done" means. Your memory file answers a different one forever — how this repository works. Paste the PRD into `CLAUDE.md` and every future session about an unrelated CSS bug pays for a finished feature's user stories. Link the PRD from the memory file instead.

One more reason, and it is the one that convinces experienced developers. A project-root `CLAUDE.md` survives `/compact`, because it is re-read from disk. Instructions you only said in chat do not. When the window fills and the conversation is summarised away, your file is the part that comes back. ([memory](https://code.claude.com/docs/en/memory))

## A working AGENTS.md you can steal

Around 40 lines, and nothing in it is readable from the code. Note the last two sections: a compaction instruction, and pointers instead of pasted docs.

```markdown
# AGENTS.md — qairu-signup

## What this is
Next.js 15 (App Router) + TypeScript + Tailwind + Supabase. UI strings in EN and KK.

## Commands
- Install: `pnpm install`
- Dev server: `pnpm dev` (http://localhost:3000)
- Typecheck: `pnpm typecheck`   Lint: `pnpm lint`
- One test file: `pnpm vitest run path/to/file.test.ts`   All tests: `pnpm test`
- E2E: `pnpm e2e` (needs dev server running)

## Workflow
- For anything bigger than a one-line change: explore, write a plan, wait for approval.
- After a series of edits run typecheck + the related tests. Show the output.
- Small commits, message = what and why. Never push to `main`; open a PR.
- If you have been corrected twice on the same thing, stop and ask.

## Code rules that differ from defaults
- Server Components by default; add "use client" only when state or effects are needed.
- All DB access goes through `src/lib/db/*`. No Supabase calls inside components.
- Every user-facing string goes through `t()` with keys in `messages/en.json` and `messages/kk.json`.
- No new dependencies without asking.

## Gotchas
- `.env.local` is required (see `.env.example`). Never print or commit secrets.
- Supabase row-level security is ON; new tables need a policy or queries return empty.
- Kazakh text: test with long words; do not truncate with fixed widths.

## Do not touch
- `supabase/migrations/*` that are already applied — add a new migration instead.
- `src/generated/*` (generated types).

## When compacting
Keep: the list of modified files, the current plan step, and the test commands.

## More detail (read only when relevant)
- Architecture: docs/architecture.md   - API conventions: docs/api.md   - Release steps: docs/release.md
```

Read it against the exclude list: no folder tour, no pasted documentation, no platitudes.

<Callout type="warn" title="The file is advice, not a fence">
The agent can read "never edit applied migrations" and still edit one. The docs call both memory systems "context, not enforced configuration". For anything that must always or never happen, back the line with a hook — a script that runs at a lifecycle event — or a deny rule in `.claude/settings.json`. ([memory](https://code.claude.com/docs/en/memory), [hooks](https://code.claude.com/docs/en/hooks-guide))
</Callout>

## The master prompt carries what the file cannot

Your memory file holds what is always true. Your prompt holds what is true today. Beginners make one do the other's job: a prompt that re-explains the stack every time, or a memory file stuffed with this week's task.

Every line in the skeleton does one job. Fill the brackets and delete nothing.

<Prompt title="Master-prompt skeleton" where="any agent · start of a task">
```text
GOAL        [one sentence: what should be true when you are done]
WHY         [who needs it / what it unblocks — helps the agent make trade-offs]
CONTEXT     Read first: @[file], @[file]. Pattern to follow: [existing example file].
            Docs: [URL]. Relevant history: [issue / PR / commit].
CONSTRAINTS Stack: [..]. Do not change: [..]. No new dependencies. Out of scope: [..].
PROCESS     1) explore and summarise  2) plan and wait for OK  3) implement in small steps
            4) verify  5) commit. Use subagents for broad searches.
DONE MEANS  [runnable check: `command` exits 0 / test names pass / screenshot matches]
            Show evidence: command + output (or screenshot).
IF STUCK    After two failed attempts at the same thing: stop, explain what you tried,
            propose options. Ask instead of guessing on anything ambiguous.
OUTPUT      Short summary: what changed, where, how verified, what is left.
LIMITS      [max turns / budget / time], then stop and report.
```
</Prompt>

`DONE MEANS` separates this from a wish. Without a check a command can run, "looks done" is the agent's only signal and you become the test suite ([module 10](/en/learn/test-and-quality/)).

`IF STUCK` mirrors a rule from the docs: after two failed corrections on the same issue, stop. A clean session with a better first prompt beats a long polluted one.

## When the answer is a subagent, not a longer file

Sometimes the knowledge fits neither a standing file nor the main conversation. The post names three techniques for long-running work: compaction (summarise and restart the window), structured note-taking (notes to a file outside the window), and sub-agent architectures.

The third is the daily habit. A subagent is a helper with its own context window. It does the noisy work — searching a large codebase, reading a log file — and returns a short summary. The raw material never enters your window. "Use subagents to investigate X" is enough to start one; the orchestration is [module 14](/en/learn/multi-agent/). ([subagents](https://code.claude.com/docs/en/sub-agents))

The trade: you get the summary, not the evidence. Ask for what you will need inside it — file paths, line numbers, the exact failing command. It prevents infinite exploration, another of the guide's five named patterns: an unscoped "investigate the codebase" fills the window before the real work starts.
