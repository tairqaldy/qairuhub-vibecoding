<Lead>
A coding agent is not faster autocomplete. It is a model handed tools — read a file, edit it, run a command, read the output — and put in *a loop* until the task is done or you stop it. This module is about who holds the leash.
</Lead>

The model is the brain. [Claude Code](https://code.claude.com/docs/en/overview) is the [harness](https://code.claude.com/docs/en/how-claude-code-works): the tools, the context management, the thing that runs the command.

## The loop you are stepping into

Five moves, repeated. You describe the task in plain language. It gathers context — files, git state, your CLAUDE.md. It acts: edits, commands. It verifies: runs the tests or the build and reads the output. Then you steer. `Esc` interrupts mid-action and keeps the work so far. Typing while it works queues a correction for after the current action.

That last move is the job. An agent stops when the work *looks* done, so give it a check it can run itself — a test, a build exit code, a linter. Otherwise you are the test suite. That is where [Anthropic's guide](https://code.claude.com/docs/en/best-practices) now starts. If you cannot verify it, do not ship it.

The same loop runs on every surface, on the same engine. CLAUDE.md, settings and MCP servers are shared across the local ones.

| Surface | Best for | Worth knowing |
|---|---|---|
| Terminal CLI | everything, plus scripting | the only surface that runs `claude -p "query"` non-interactively |
| Desktop app | visual diffs, parallel sessions | includes Claude Code, no CLI install; paid plan required |
| Web, [claude.ai/code](https://claude.ai/code) | long jobs you walk away from | runs in Anthropic-managed cloud VMs after you disconnect |
| VS Code / JetBrains | inline diffs, plan review in the editor | the VS Code extension bundles its own CLI and does **not** put `claude` on your PATH; the JetBrains plugin needs the CLI installed separately |

## Permission modes are a trust dial

Every action is allowed, asked about, or denied. The mode decides which.

| Mode (UI label) | Config value | Runs without asking |
|---|---|---|
| Manual | `default` | reads only |
| Accept edits | `acceptEdits` | reads, file edits, common file commands in the working directory |
| Plan | `plan` | reads and exploration; no source edits until you approve a plan |
| Auto | `auto` | everything, with a separate classifier model reviewing each action |
| Don't ask | `dontAsk` | only pre-approved tools, everything else denied — for CI |
| Bypass permissions | `bypassPermissions` | everything, no review |

`Shift+Tab` cycles them; the status bar says where you are. `claude --permission-mode plan` starts you in one. A repo cannot trap you: `auto` and `bypassPermissions` are ignored when a project's own `.claude/settings.json` sets them.

On Pro, Max and Team plans, interactive terminal and VS Code sessions now start in **auto**. Enterprise plans, Console API keys and every `claude -p` run still start in Manual. "Claude Code asks about everything by default" is out of date.

  <Stat value="17%" label="of genuinely over-eager actions the classifier misses" source="Anthropic, Mar 2026" href="https://www.anthropic.com/engineering/claude-code-auto-mode" tone="warn" />
  <Stat value="84%" label="fewer prompts with OS-level sandboxing" source="Anthropic, Oct 2025" href="https://www.anthropic.com/engineering/claude-code-sandboxing" tone="good" />
</StatRow>

Auto mode exists because of the first number. Anthropic's post: "Claude Code users approve 93% of permission prompts." That is reflex, not review — the post calls it approval fatigue. So a second model reviews each action instead of you and blocks what escalates beyond the ask. False positives: 0.4%. It cuts prompts; it does not guarantee safety. A seatbelt, not a cage.

<Callout type="danger" title="What bypassPermissions actually risks">
`bypassPermissions` (the `--dangerously-skip-permissions` flag) removes the asking entirely: no prompts, no classifier. Every command it decides to run, runs — deleting files, pushing to a remote, sending data somewhere. The docs restrict it to containers and VMs; on a laptop holding your SSH keys and `.env` files it is a bad trade. Two things survive even there: `deny` rules win in every mode, and `rm -rf /` or `rm -rf ~` are never auto-approved.
</Callout>

<Deeper title="What auto mode blocks — and why a sandbox is a different thing">
The classifier blocks download-and-execute patterns like `curl | bash`, sending sensitive data out, production deploys and migrations, mass cloud deletion, permission grants, force pushes and `git reset --hard` discards of uncommitted work. Say "don't push" in chat and it holds that boundary until you lift it.

Sandboxing (`/sandbox`) is different: OS-level filesystem and network isolation for the Bash tool. It runs on macOS, Linux and WSL2 — **not** native Windows, which is most of this room. There your controls are allow/deny rules and Manual mode, and they match command text, not programs: `Bash(rm *)` will not stop a Python script that deletes the same file. Convenience, not a security boundary.
</Deeper>

## Plan mode: argue with the plan, not the diff

In plan mode the agent reads and explores but cannot touch your source. It comes back with a plan; `Ctrl+G` opens it in your editor so you can rewrite it before approving. One constraint added to a plan costs a sentence. The same constraint pulled out of finished code costs an afternoon. On approval you pick: auto mode, manual approval of each edit, or "No, keep planning".

The shape is explore, plan, implement, commit. Skip the plan when you could describe the diff in one sentence — a typo, a rename, a log line. Plan when the approach is uncertain, the change spans files, or the code is new to both of you.

## What it loads before you type

`CLAUDE.md` is read whole at the start of every session, broad to specific: `~/.claude/CLAUDE.md`, then `./CLAUDE.md` or `./.claude/CLAUDE.md`, then a gitignored `./CLAUDE.local.md`. Since v2.1.277 Claude Code also reads a repo's `AGENTS.md` when no CLAUDE.md exists — the file Codex, Cursor, Copilot and Jules read too. What goes inside it is [module 06](/en/learn/context-ssot/). Two things matter here: under 200 lines, because bloat makes rules get ignored; and it is context, not enforcement — to truly block something, use a deny rule or a hook.

Everything shares one context window, and quality drops as it fills ([module 02](/en/learn/ai-in-plain-language/)). Four commands: `/context` shows what is eating the window, `/clear` starts a fresh conversation for free, `/compact keep the API decisions and the file list` summarises on your terms, `/btw what does localStorage do?` asks a side question that stays out of the history. The docs' rule: corrected it twice on the same thing? `/clear` and write a better prompt.

## Rewind is local undo. Git is real undo.

Every prompt that starts a turn creates a checkpoint. `Esc` `Esc` on an empty input (or `/rewind`) opens the menu: restore code and conversation, restore one, or summarise part of the session. The last 100 per session are kept; snapshots are swept after about 30 days.

Checkpoints track edits made by Claude's own edit tools. They do **not** track files changed by Bash commands, most subagent edits, your own manual edits, or anything remote — a database write, a deploy, a push. That is the whole argument for `git init` and a commit before you let an agent run ([module 09](/en/learn/git-and-github/)).

## Four ways to teach it once

**Skills** are a folder with a `SKILL.md` in `.claude/skills/<name>/`. Only the description sits in context; the body loads when needed. That is why a skill beats another page bolted onto CLAUDE.md. Call it as `/name`, or let the agent pick it up when the description matches. It follows the open [Agent Skills](https://agentskills.io) standard, so skills are not Claude-only.

**Subagents** are helpers with their own context window, tools and permissions. They do the noisy work — searching a big repo, reading a log — and return a summary, so the mess lands in their window, not yours. Explore, Plan and general-purpose are built in; yours live in `.claude/agents/<name>.md`. `/rewind` usually does not restore their edits.

**Hooks** are your own shell commands, run at lifecycle events: `PreToolUse` (exit code 2 blocks the action), `PostToolUse`, `Stop`, `Notification`. Unlike a line in CLAUDE.md, a hook always fires — the difference between "please run the formatter" and a formatter that runs.

**MCP** plugs external tools and data into an agent — issue trackers, databases, browsers, design tools ([module 02](/en/learn/ai-in-plain-language/)). The cleanest first server is the Claude Code documentation itself.

<Terminal title="bash">
```bash
claude mcp add --transport http claude-code-docs https://code.claude.com/docs/mcp
claude mcp list
# claude-code-docs ... Connected
```
</Terminal>

Now it looks up its own docs instead of guessing at a flag. The classic mistake: dropping the `--` when the server is a local command (`claude mcp add playwright -- npx -y @playwright/mcp@latest`). Everything after `--` starts the server. MCP tool definitions load on demand, so they cost little context — but a plain CLI like `gh` is still cheaper for the same job.

<Callout type="live" title="For the room">
Do the mode cycle live, first thing: start a session, press `Shift+Tab` four times, read the status bar aloud each time. Thirty seconds, and most beginners do not know it exists.
</Callout>

<Deeper title="The habits are portable. The tools are not.">
In one year: Gemini CLI paywalled its consumers, Windsurf became Devin Desktop, Roo Code's repo was archived on 15 May 2026, Cursor was acquired for $60B, and GitHub swapped Copilot's premium requests for token-metered credits. What survives a rename is your habits — an `AGENTS.md` at the repo root, a commit before every agent run, a plan you read before code exists, a test the agent has to pass.

The agent stayed sandboxed; trusted tools outside it later ran the files it wrote. Treat a cloned repo's text as untrusted input, and never run unfamiliar code in a permissive mode.
</Deeper>

## Six parts of a prompt that works

The gap between a disappointing result and a good one is almost never the model. It is what you left out.

<Compare a="What most people type" b="What the agent can act on">
<div slot="a">
"fix the signup bug"

It does not know what the bug looks like, which file to open, what "fixed" means, or when to stop. It guesses all four, and you get a diff that solves a different problem.
</div>
<div slot="b">
"Users with a `+` in their email get 'invalid address' on submit. Expected: accepted. Likely in `src/lib/validate.ts`. Write a failing test first, then the smallest fix. Run `npm test` and show me the output."

Symptom, location, definition of done, and a check it can run itself.
</div>
</Compare>

You rarely need all six at once:

1. **Role** — the standard it judges its own work against. "You are a senior frontend engineer who values boring, readable code."
2. **Goal** — one sentence with a finish line. "Make it better" has none.
3. **Context** — files to read first, the pattern to copy, the stack. Without it the agent invents a stack that is not yours.
4. **Constraints** — what not to touch, no new dependencies, what is out of scope. Named before they happen, not after.
5. **Output shape** — "show me the diff for each file before applying it" decides whether you review the work or just receive it.
6. **Stop condition** — "if anything is ambiguous, ask me instead of guessing; stop after the tests pass". The highest-value line in most prompts.

When a result disappoints, walk this list before reaching for a bigger model. It is usually 3 or 6.

## The prompt pack you will actually reuse

Square brackets are yours to fill in. Nothing here is Claude-specific: these work in Codex, Cursor, Copilot and Kiro too.

<Prompt title="1. PRD prompt — interview me, then write the spec" where="Any agent · fresh session">
```text
I want to build: [one or two sentences].

Before writing anything, interview me. Ask one question at a time.
Skip obvious questions; dig into what I probably have not thought through:
- who the user is and the single most important job they need done
- the smallest version that is still useful, and what is explicitly OUT of scope
- data: what is stored, where, who can see it
- edge cases, failure states, empty states
- tech constraints: [stack / hosting / budget / deadline]
- how we will know it works (checks a script or a person can run)

Stop when you have enough, then write SPEC.md with these sections:
1. Problem and user  2. Goals / Non-goals  3. User stories with acceptance criteria
4. Data model  5. Screens or endpoints  6. Tech decisions and why
7. Out of scope  8. End-to-end verification steps  9. Open questions

Do not write code. I will review SPEC.md and start a fresh session to build it.
```
</Prompt>

<Prompt title="2. Plan prompt — read, propose, then wait" where="Claude Code · plan mode">
```text
Read SPEC.md and the existing code under [paths]. Do not edit anything yet.

1. Tell me what you found: relevant files, existing patterns to reuse, risks.
2. Propose an implementation plan as PLAN.md:
   - ordered steps, each small enough to verify on its own
   - files to create or change per step
   - the test or check that proves each step works
   - what you will NOT touch
   - questions or assumptions I must confirm
3. Offer one simpler alternative if there is one, with the trade-off.

Wait for my approval before implementing. If a step turns out wrong while
implementing, stop and update the plan instead of improvising.
```
</Prompt>

<Prompt title="3. Bug-fix prompt — reproduce before you fix" where="Any agent · after a commit">
```text
Bug: [what the user sees]. Expected: [what should happen].
Where: [page / endpoint / file guess]. Since: [commit, date, or "unknown"].
Evidence: [paste error, log lines, screenshot].

Process:
1. Reproduce it. Write a failing test (or a script) that shows the bug. Show me the failure.
2. Find the root cause. Explain it in 3-5 sentences. Do not hide the symptom
   (no try/catch that swallows it, no skipped or deleted tests).
3. Fix it with the smallest change. Run the new test and the related suite.
4. Show evidence: the command you ran and its output.
5. Tell me if the same mistake likely exists elsewhere; list places, do not fix them yet.

Do not refactor unrelated code. Commit with a message that explains the cause.
```
</Prompt>

<Prompt title="4. Refactor prompt — behaviour must not change" where="Any agent · tests passing first">
```text
Refactor [file or module] so that [specific goal]. Behaviour must not change.

Before you start: run [test command] and show me it passes. If it does not, stop and tell me.

Rules:
- No new features, no new dependencies, no change to the public interface
  unless I approve it first.
- One kind of change per commit: structural OR behavioural, never both.
- Never delete, skip or weaken a test to get the suite green.
- If you need to change behaviour to make this work, stop and explain why.

After: run the same tests, show the output, and give me three bullets on what
moved where and what is now easier to change.
```
</Prompt>

<Prompt title="5. Review prompt — a fresh pair of eyes" where="Fresh session or subagent">
```text
You are reviewing a change you did not write. Use a fresh session or subagent.
Inputs: the diff of [branch or PR], SPEC.md / PLAN.md, and AGENTS.md.

Check, in this order:
1. Correctness: does it do what the spec says? Which requirement is missing or wrong?
2. Edge cases from the spec: is each one handled AND tested?
3. Security: input validation, auth checks, secrets in code, injection, unsafe defaults.
4. Scope: anything changed that the task did not require?
5. Tests: would they fail if the feature broke? Any test weakened, skipped or deleted?

Report only findings that affect correctness, security or the stated requirements.
For each: file and line, what breaks, a concrete failing scenario, suggested fix.
Put style preferences in a separate, optional list. If you find nothing serious, say so.
```
</Prompt>

<Prompt title="6. Test prompt — red, then green" where="Any agent · red/green TDD">
```text
Add tests for [function / module / flow] in [path]. Use red/green TDD.

- Read the existing tests first and copy their style and runner ([runner]).
- Cover: the happy path, [edge case 1], [edge case 2], invalid input, and one
  regression for [past bug] if relevant. Avoid mocks unless the dependency is
  external or slow.
- For new behaviour: write the test, run it, show me it FAILS for the right reason,
  then implement until it passes.
- For existing behaviour: if a new test fails, stop and tell me — it may be a real bug.
  Do not change production code to make a test pass without asking.
- Run only the relevant tests while iterating, the full suite once at the end.
  Show the final output.
Never delete, skip or loosen an existing test to get green.
```
</Prompt>

The red step in prompt 6 exists because a test you never saw fail may be passing for the wrong reason ([Simon Willison](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)). The structural/behavioural split in prompt 4 is [Kent Beck's](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes). He also names three signs an agent is off the rails: it loops, it adds what nobody asked for, it disables tests.
