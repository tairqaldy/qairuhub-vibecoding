## The terminal is a text box, not a test

You type commands instead of clicking. That is precise, scriptable, and identical on any machine.

It matters now because Claude Code runs inside it. It prints every command it runs and every line of output. Read that, and you can judge what you are approving.

A terminal does nothing until you press Enter. And when something fails, the error text on screen is the most useful thing in the room.

<Callout type="tip" title="You are already in one">
Claude Code is a terminal program. Inside a session, `!` at the start of a line runs a shell command and drops the output into the conversation; `@` autocompletes a file path ([interactive mode](https://code.claude.com/docs/en/interactive-mode)). The commands below are the same skill, not a separate one.
</Callout>

## Every command happens somewhere

A terminal always stands inside one folder — the current directory — and most commands act on it. Beginner confusion ("the command did nothing", "file not found") is usually "I was standing in the wrong place".

A path is the address of a folder or file. `/` separates the parts on macOS, Linux, WSL and Git Bash; `\` on native Windows. The Claude Code binary lands at `~/.local/bin/claude` on macOS and Linux, at `%USERPROFILE%\.local\bin\claude.exe` on Windows ([setup docs](https://code.claude.com/docs/en/setup)). `~` means your home folder. `.` means here. `..` means one level up.

One rule: always `cd` into your project folder before starting an agent. Start it on the Desktop instead and every other project you own sits inside its working directory. One project, one folder, one session.

## Ten commands cover almost every tutorial

| Command | What it does |
|---|---|
| `pwd` | print where you are |
| `ls` | list what is in this folder |
| `cd name` | go into a folder |
| `cd ..` | go back up one level |
| `cat file` | print a file to the screen |
| `mkdir name` | make a folder |
| `touch name` | make an empty file |
| `cp a b` | copy a to b |
| `mv a b` | move or rename |
| `rm name` | delete |

On Windows these work as written in Git Bash. PowerShell answers to most of them; `touch` is the usual miss. CMD does not.

Two keys beat every command in that table. Up brings back what you last typed. Tab completes a half-finished name, in a real terminal.

<Terminal title="bash">

```bash
pwd
cd qairu-event
ls
cat package.json
cp .env.example .env
```

</Terminal>

<Callout type="danger" title="rm is not the Recycle Bin">
`rm` deletes immediately, with no undo and no confirmation. Your agent's safety net does not cover it: Claude Code [checkpoints](https://code.claude.com/docs/en/checkpointing) do not track files changed by Bash commands such as `rm`, `mv` or `cp`, or remote side effects like deploys and pushes. Git commits are the real undo ([module 9](/en/learn/git-and-github/)).
</Callout>

Try them in a terminal that cannot hurt you.

## node_modules is not your code

A package manager downloads the libraries your project needs, plus the libraries those need, and records the exact versions in a lock file so every machine installs the same thing. For JavaScript that is npm, pnpm or bun; for Python, pip or uv.

- **`package.json`** — what you asked for: the dependencies and the named commands (`dev`, `build`, `test`).
- **the lock file** — what you actually got, down to the exact version.
- **`node_modules/`** — the downloaded code itself. Hundreds of folders. Nobody reads it.
- **`npm install`** — the command that turns the first two into the third.

`node_modules` never goes into git: it is enormous, and one command rebuilds it anywhere. A Claude Code git worktree is a fresh checkout with no `node_modules`, so you reinstall it ([worktrees](https://code.claude.com/docs/en/worktrees)). If an agent proposes committing that folder, say no.

## localhost is your house, not the internet

`npm run dev` looks up `dev` in `package.json` and runs it. That starts a dev server: a small web server on your own machine. It serves your project to your browser and reloads the page when you save a file.

It prints an address, usually `http://localhost:3000`. A second project or a second server prints a different number, so read it off your own screen rather than memorising it.

Three habits:

1. Give the dev server its own terminal tab. It keeps running and printing; it is not frozen.
2. `Ctrl+C` stops it. "Port already in use" almost always means you started a second one.
3. A blank page with no errors is still progress. Before you call it broken, read the terminal output and the browser console. Paste both to the agent.

## .env holds the keys, and it never leaves your laptop

Environment variables are named values that live outside your code and reach the program when it starts: API keys, a database address, `NODE_ENV=production`. They keep secrets out of the repository, and let the same code behave differently on your laptop and on the server. Locally they sit in a `.env` file listed in `.gitignore`. On a host you paste them into the dashboard.

One correct order, no exceptions:

<Compare a="What beginners do" b="What you do">
<div slot="a">
Build the app. Get it working. Run `git init`, commit everything, push to GitHub. Add `.gitignore` later, when a tutorial mentions it.

The key is now in the repository history. Deleting the file does not remove it. The only fix is to revoke that key and issue a new one.
</div>
<div slot="b">
Create `.gitignore` with `.env` and `node_modules/` in it **before the first commit**.

Commit a `.env.example` with the key names and empty values. Anyone — you on a new laptop included — then knows which variables the project needs, without seeing a real one.
</div>
</Compare>

Keys have no place in the frontend either. It runs on the user's device, and anyone can read it in the browser developer tools. They belong on the backend or in the host's dashboard ([module 11](/en/learn/security/)).

<Deeper title="Can I just tell my agent not to read .env?">
You can, and you should — but it is not a lock. In [`.claude/settings.json`](https://code.claude.com/docs/en/settings) a rule like `"deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]` blocks the Read tool, plus `cat`, `head`, `tail` and `sed` in Bash. It does not stop a script that opens the file itself: Bash rules match command text, not the program. The [permissions docs](https://code.claude.com/docs/en/permissions) are plain about it — convenience, not a security boundary. Real isolation comes from sandboxing, which native Windows does not support. Rotate any key that has ever been committed or pasted into a chat.
</Deeper>

## "It works on my machine" is a diagnosis, not a joke

It means your machine has something the other machine does not. Five usual candidates, all checkable in two minutes.

- **A missing environment variable.** Your `.env` exists locally and nowhere else. Fix: add the variables in the host dashboard.
- **An uncommitted file.** It works because the file is on your disk, not in the project. Fix: `git status`.
- **Dependencies never installed.** The other machine has `package.json` but no `node_modules`. Fix: run the install command.
- **Capital letters.** Windows treats `Hero.astro` and `hero.astro` as the same file. Most deploy servers run Linux and treat them as two, so an import that works locally fails in the build. Fix: match the filename character for character.
- **A different version.** A newer or older runtime than yours. Claude Code shows the pattern: the npm install route needs Node.js 22 or newer ([setup docs](https://code.claude.com/docs/en/setup)).

Working on your machine is not done. Deployed is done ([module 12](/en/learn/deploy/)).

## If you are on Windows, read this part twice

Most of this course's audience is on Windows. Most tutorials are not. You do not need Linux: Claude Code runs natively on Windows 10 1809 or newer with 4 GB of RAM or more, from PowerShell or CMD. WSL is **not** required — WSL 2 only matters if you want Claude Code's sandboxing, which native Windows does not support ([setup docs](https://code.claude.com/docs/en/setup)).

Install [Git for Windows](https://git-scm.com/downloads/win) anyway. With it, Claude Code uses Git Bash for its Bash tool; without it, a PowerShell tool. Module 9 needs git regardless.

First, know which shell you are looking at.

| The prompt line | The shell | So |
|---|---|---|
| `PS C:\Users\you>` | PowerShell | install commands written for PowerShell belong here |
| `C:\Users\you>` | CMD | install commands written for CMD belong here |
| `you@laptop:~$` | Git Bash or WSL | the macOS/Linux commands in tutorials work as written |

Then read the error instead of retrying it.

| The message | What actually happened |
|---|---|
| `The token '&&' is not a valid statement separator` | you pasted a CMD command into PowerShell |
| `'irm' is not recognized` | you pasted a PowerShell command into CMD |
| `'claude' is not recognized` | the install folder is not on PATH — fix it, then open a **new** terminal |
| `Claude Code does not support 32-bit Windows` | you opened "PowerShell (x86)" instead of PowerShell |

All four come from the official [setup](https://code.claude.com/docs/en/setup) and [install troubleshooting](https://code.claude.com/docs/en/troubleshoot-install) pages. PATH is the most common. Fix it, then open a fresh window — a running terminal never notices a PATH change:

<Terminal title="powershell">

```powershell
$currentPath = [Environment]::GetEnvironmentVariable('PATH', 'User')
[Environment]::SetEnvironmentVariable('PATH', "$currentPath;$env:USERPROFILE\.local\bin", 'User')
```

</Terminal>

<Callout type="live" title="For whoever is teaching this">
Do the shell table live. Before anyone installs anything, ask the room to read out their own prompt line. Two minutes here saves most of the install firefighting in the lab.
</Callout>

## Make the agent give you the tour

You do not have to read a project to learn its layout. Ask — then check every answer with the commands above.

<Prompt title="Bench check" where="Claude Code · in your project folder">

```text
I am new to the terminal. In this project, do these four things and explain each one in two sentences:

1. Show me the folder structure, ignoring node_modules and .git.
2. Tell me the exact command that starts the dev server and the address it will print.
   Read this from package.json - do not guess.
3. Check whether .gitignore contains .env and node_modules. If either is missing, show me
   the line you would add before you add it.
4. List every environment variable this project reads, by name only. Never print a value.

Change nothing else. If you are unsure about something, say so instead of guessing.
```

</Prompt>

<ProjectStep n={8} title="Set up the bench before you ask for a single feature">
1. `mkdir qairu-event`, then `cd qairu-event`. One project, one folder, nothing loose on the Desktop.
2. Let the agent scaffold the project. Then run the install command and start the dev server **yourself**, so you have typed them once.
3. Open the address the terminal printed. A nearly empty page counts.
4. Create `.gitignore` containing `.env` and `node_modules/`. Create `.env.example` with key names and empty values, and `.env` with the real ones. In that order, before module 9 turns this folder into a repo.

You are done when you can change one word in the page, see it update in the browser, stop the server with `Ctrl+C`, and start it again from memory.
</ProjectStep>
