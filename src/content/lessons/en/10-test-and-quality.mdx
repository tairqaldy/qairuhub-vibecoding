<Lead>
When an agent says the feature works, it is not reporting. It is *guessing* — a well-informed guess about what would happen if somebody ran the code. A test is different: somebody ran it, and this is the output.
</Lead>

## The agent stops when the work looks done

Anthropic's guide for Claude Code opens with "Give Claude a way to verify its work" — first on the page, before planning, before context ([code.claude.com/docs](https://code.claude.com/docs/en/best-practices)).

The agent needs a signal to decide it is finished. Without one, the only signal left is *this looks finished*. Then you are the test suite: you click around, find the broken thing, paste it back. On every feature, for the rest of the project.

The most common complaint is not wrong answers. It is nearly-right ones.

<StatRow>
  <Stat value="66%" label="frustrated by AI answers that are almost right, but not quite" source="Stack Overflow 2025" href="https://survey.stackoverflow.co/2025/ai" tone="warn" />
  <Stat value="45%" label="say debugging AI-generated code takes them longer" source="Stack Overflow 2025" href="https://survey.stackoverflow.co/2025/ai" tone="warn" />
</StatRow>

Almost-right code is expensive because it passes a human glance. It does not pass a test.

## A check is anything that returns pass or fail

You do not need a testing framework. A check is anything the agent can run that comes back yes or no. The Claude Code guide lists the usual ones: a test suite, the build exit code, a linter, a script that diffs your output against a fixture, a browser screenshot compared against a design.

Four ways to make the agent obey a check, in rising order of setup:

1. **Ask in the prompt.** "Run `npm test` and keep going until it passes. Show me the output." Free, and it usually works.
2. **`/goal <condition>`.** Claude Code runs a separate small model that re-checks your condition after every turn.
3. **A Stop hook.** A script that will not let the turn end until your command exits zero. Claude Code overrides it after eight consecutive blocks, so it is a strong nudge, not a cage.
4. **A verification subagent** — a fresh model whose only job is to try to refute the result.

Two rules from the same page. Ask for evidence — the command and its output — not assertions. If you cannot verify it, do not ship it.

<Callout type="warn" title="The agent is not lying to you">
"All tests pass" can be true and useless at once. The tests may have been written after the code, from the code, describing whatever it happens to do. That is the failure mode this module is built around.
</Callout>

That is where you end up after a year, not where you start. With zero tests, write one test at the top: the single path your product exists for. For QAIRU Event Sign-up that is *open the page, fill in a name and an email, press reserve, see a confirmation*.

Then push downward and let the bugs choose. Every time something breaks, that bug becomes a unit test before it becomes a fix. Anthropic's [bug-fix pattern](https://code.claude.com/docs/en/best-practices) is the same: describe the symptom, the likely location and what "fixed" means, ask for a failing test that reproduces it, then the fix. Your suite fills with real failures, not imagined ones.

## Write the test that fails, then let it code

Red/green TDD fits agents better than it ever fit humans. Simon Willison's one-line version: add "Use red/green TDD" to a build prompt. The agent writes the test, watches it fail, then implements until it passes ([Agentic Engineering Patterns](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)).

The red step is the part people skip, and the part that carries the value. A test you never saw fail might pass for the wrong reason: it may assert nothing, or keep passing after you delete the feature. Red first is the proof that it is wired to the behaviour it checks.

Four reasons it suits an agent:

- **The loop closes without you.** The agent runs the test, reads the failure, iterates. You no longer stand between attempt one and attempt two.
- **It bounds the work.** Red/green guards against code that does not work *and* against extra code nobody asked for. The test is the edge of the task.
- **It survives the session.** The next session starts with no memory of this one. The test does not.
- **The agent optimises for whatever you measure.** Anthropic built a C compiler with sixteen parallel Claude instances; the lesson was that the agent solves exactly the problem the tests define ([building a C compiler](https://www.anthropic.com/engineering/building-c-compiler)). Strong tests, right product. Weak tests, confidently wrong product.

<div slot="a">

**"Add duplicate-email checking to the sign-up form, and add tests."**

The agent writes the feature, then tests that describe what it just wrote. Everything is green, nothing is proven: if the feature has a hole, the test was written from the code with the hole.

</div>
<div slot="b">

**"Write one failing test for duplicate emails. Run it. Show me the failure. Stop."**

<Prompt title="Red/green: the failing test first" where="Claude Code · after /clear">
```text
Feature: [one sentence — what must be true when this works].
Files I expect this to touch: [path, or "you decide, but tell me first"].

Use red/green TDD, in this order:
1. Read the existing tests in [test dir] first. Copy their style and their runner.
2. Write ONE failing test for the behaviour above. Nothing else. No production code yet.
3. Run it. Paste the failure output and tell me in one sentence why it fails.
   Then STOP and wait for my OK.
4. After my OK: write the minimum code to make that test pass.
   Run only that test while iterating.
5. Run the full suite once at the end. Paste the final output.

Rules:
- Never delete, skip, or loosen an existing test to get green.
- If an existing test starts failing, stop and tell me. It may be a real bug.
- No extra features, no refactors I did not ask for.
```
</Prompt>

<Callout type="danger" title="Three signs the agent is cheating">
Kent Beck named three signals in June 2025: it **loops** on the same fix; it adds **functionality nobody asked for**; it **disables or deletes tests to get green** ([Augmented Coding, 25 Jun 2025](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)). The third is the dangerous one: your screen still says "all tests pass". Read the diff for deleted or skipped test files every time.
</Callout>

## One end-to-end test for the path that matters

Unit tests check functions. Only an end-to-end test checks the product. Playwright drives a real browser through your app — the same tool Anthropic's long-running harness hands an evaluator agent ([harness design, 24 Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps); long runs are [module 15](/en/learn/overnight-builds/)).

Set it up once:

<Terminal title="bash">
```bash
npm init playwright@latest
# choose TypeScript, put the tests in ./e2e, let it install the browsers
npx playwright test
```
</Terminal>

The whole test for QAIRU Event Sign-up:

```ts
// e2e/reserve-seat.spec.ts
import { test, expect } from '@playwright/test';

test('a visitor can reserve a seat and sees a confirmation', async ({ page }) => {
  await page.goto('http://localhost:3000/');
  await expect(page.getByRole('heading', { name: 'QAIRU Meetup' })).toBeVisible();

  await page.getByLabel('Name').fill('Aiganym');
  await page.getByLabel('Email').fill('aiganym@example.kz');
  await page.getByRole('button', { name: 'Reserve a seat' }).click();

  await expect(page.getByText('Seat reserved')).toBeVisible();
});
```

Read it out loud: it is what a person does. It fails when a human would fail, not when a function signature changes. It finds elements by visible role and label, not by CSS class — a restyle does not break it, removing the button does.

Your `AGENTS.md` ([module 06](/en/learn/context-ssot/)) promises an E2E command. Now one exists, so make that line true — an agent cannot guess a command it has never seen:

```markdown
## Commands
- E2E: `npx playwright test` (needs the dev server running on port 3000)
```

This is not about AI writing bad code. It is about what *unreviewed* AI code does to a repository. Asked to add a feature, an agent will write a fifth copy of a function that already exists four times: writing is cheap, searching costs context ([module 02](/en/learn/ai-in-plain-language/)). Nobody chose that debt — no human read the diff.

<Deeper title="How much to trust these numbers">
GitClear sells code-quality tooling, and the study is correlational — no AI-versus-non-AI control group. Its "moved lines" metric can also undercount refactoring when an agent rewrites a function in place. A vendor study from [CodeRabbit](https://www.coderabbit.ai/newsroom/state-of-ai-vs-human-code-generation-report) (17 Dec 2025, 470 open-source PRs) found AI-co-authored pull requests carried about 1.7x more issues — 10.83 versus 6.45 per PR — with logic errors 1.75x higher. Human PRs had 1.76x more spelling errors and 1.32x more testability issues. Nobody here is clean. Treat it as a direction, not a measurement.
</Deeper>

Five things to look for in an AI diff, in this order.

1. **Does it do what you asked?** Not "does it look reasonable" — does it meet the requirement. Name the one it misses.
2. **Would the tests fail if the feature broke?** Delete the feature mentally and ask which test goes red. If none, the tests are decoration.
3. **Was anything swallowed?** An empty `catch`, a default that hides a missing case, a `try` that turns a crash into silence. This failure reaches production and never shows up in a log.
4. **Does this code already exist?** Duplication is the clearest signal in the numbers above, and the easiest to catch — you just have to ask.
5. **What changed that you did not ask for?** Scope creep is common in agent diffs, and it is where risk hides.

Input validation, auth checks and secrets in code go on this list too; the rest is [module 11](/en/learn/security/).

<Prompt title="Adversarial self-review of the diff" where="Claude Code · fresh session (/clear first)">
```text
You are reviewing a change you did not write. Start by reading it: `git diff main...HEAD`.
Your job is to find what is wrong with it, not to defend it. Assume it is flawed.

Check, in this order:
1. Correctness: does it do what [SPEC.md / the task] says? Name what is missing or wrong.
2. Edge cases: empty input, a duplicate submit, very long text, non-Latin characters,
   the network call failing. For each: is it handled AND tested?
3. Tests: which of these tests would still pass if I deleted the feature entirely?
   List them by name. Was any test skipped, weakened, or deleted in this diff?
4. Hidden failure: every catch block that swallows an error, every default value
   that masks a missing case.
5. Duplication: is there code here that already exists elsewhere in this repo?
   Show me both copies with file and line.
6. Scope: anything changed that the task did not require?

For each finding give: file and line, what breaks, a concrete failing scenario, a fix.
Put style opinions in a separate list at the end.
If you genuinely find nothing serious, say so plainly — do not invent findings.
```
</Prompt>

## Let a second agent try to break it

The pattern above has a name: Anthropic's **evaluator-optimizer** loop. One model generates, a second critiques against explicit criteria, and it goes round until the critic is satisfied ([19 Dec 2024](https://www.anthropic.com/engineering/building-effective-agents)).

Agents grade their own work too generously, so the evaluator stays separate and drives the running app instead of reading the code. Day to day that is a verification subagent, told to run the complete suite before it passes anything ([multi-agent guidance, January 2026](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them); wiring those up is [module 14](/en/learn/multi-agent/)).

You need none of that today. `/clear`, then paste the review prompt. A fresh context reviews better because it is not attached to code it wrote.
