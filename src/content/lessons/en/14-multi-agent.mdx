Anthropic's research system runs a lead agent that fans out to subagents. It beats a single agent by a wide margin on their internal eval, and spends roughly fifteen times the tokens of a chat. Multi-agent is not *free speed*. It is a trade.

Everything so far took one agent, one session, one terminal. That is still right for most work. This module is about the exceptions.

## Start by assuming you do not need this

Anthropic's January 2026 guidance puts the order first: exhaust one agent before you add a second. A sharper prompt, a `/clear`, a plan you actually read cost nothing. A second agent typically costs [three to ten times the tokens](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) for the same task.

Walden Yan's [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) at Cognition, June 2025, argues the other side. Agents must share the full trace, not a tidy summary, because every action carries a decision the agent never announces. Two subagents build one game — a Mario-style background, a bird that does not match — and the lead merges incompatible assumptions. (Its line about subagents not writing code in parallel was true in mid-2025, not now.)

<Callout type="warn" title="Parallel agents do not fail loudly">
They rarely crash. Each one produces something reasonable, and the pieces contradict each other. You find out at merge time — the most expensive moment possible.
</Callout>

## Three reasons to split, and one bad way to split

The January 2026 post names three cases where a second agent earns its keep. **Context protection**: the side work would flood your main window. **Parallelisation**: the facets are genuinely independent. **Specialisation**: a narrow tool set or prompt beats a generalist.

<Compare a="Split by job title" b="Split by context">
<div slot="a">
A planner plans, a coder codes, a tester tests. Each handoff drops what the previous agent knew but never wrote down. The tester tests what it guessed the feature was.
</div>
<div slot="b">
The agent that builds a feature writes its tests too — it already holds the context. Split when the context is separate: a different module, a different file set, a question answerable without the rest.
</div>
</Compare>

## Five shapes, and the one Anthropic actually shipped

The vocabulary comes from [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) by Erik Schluntz and Barry Zhang, December 2024. Five patterns, three of which you have already used. Its advice has aged well: start simple, add complexity only when it measurably improves the result.

| Shape | What it is | Where you have met it |
| --- | --- | --- |
| Prompt chaining | Each step's output is the next step's input | Explore → plan → code → commit |
| Routing | Classify the input, send it to the right specialist | `model: haiku` for cheap work, Opus for architecture |
| Parallelisation | Independent slices at once (sectioning), or the same slice several times and compared (voting) | `/batch`, two worktrees |
| Orchestrator-worker | A lead decides the split at runtime, then delegates | The research system below |
| Evaluator-optimizer | One generates, a second critiques, loop | A fresh-context reviewer on your own diff |

The worked example is Anthropic's [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system), June 2025: a lead Opus 4 agent plans the search and spawns Sonnet 4 subagents in parallel, each searching in its own clean window and returning a condensed summary. It beat single-agent Opus 4 by 90.2% on their internal research eval.

Now the honest half. Token usage alone explained about 80% of the performance variance on a browsing benchmark — it works largely because it spends more tokens, in more windows, at once. Tasks with shared context or many dependencies are a poor fit, and coding has fewer parallel parts than research.

<Deeper title="The summary is the trick, not the parallelism">
Anthropic's [context engineering post](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) lists three techniques for long-horizon work: compaction, notes on disk outside the window, and sub-agent architectures.

Read that as compression. A subagent reads forty files and hands back one paragraph; the lead's window pays for the paragraph, not the files ([module 02](/en/learn/ai-in-plain-language/)). A subagent that dumps its whole transcript back gives you nothing. The output contract is the most important line in a subagent definition.
</Deeper>

## What this looks like in Claude Code tonight

The [docs put every parallel option on one page](https://code.claude.com/docs/en/agents), in rising order of how much rope you hand over:

- **Subagents.** Workers inside one session, each with its own context window, tools and model. Define one at `.claude/agents/<name>.md`; set `model: haiku` for cheap work and `isolation: worktree` when it edits files. They nest three layers below the main conversation, and spawning fails once twenty run at once.
- **Worktrees.** A second working directory of the same repo on its own branch ([module 09](/en/learn/git-and-github/)), so two sessions can never touch the same file. Not a way to go parallel — the layer that stops collisions.
- **Background and cloud sessions.** `claude agents`, a research preview, dispatches and monitors background sessions from one screen, each moving into its own worktree before editing. `claude --cloud` runs the task in an Anthropic-managed VM that clones your branch, so push first; `claude --teleport` brings it back.
- **Agent teams.** A lead plus teammates with a shared task list and a mailbox. Experimental, off by default. Three to five teammates, five or six tasks each, one owner per file. Teammates are *not* worktree-isolated, so partitioning files is your job.
- **Dynamic workflows.** Claude writes a script that a runtime executes in the background; only the final answer returns to your context. Sixteen concurrent agents by default, a thousand per run, a warning past about twenty-five.

<Terminal title="bash">
```bash
# one isolated checkout per parallel task
claude --worktree signup-form
# -> .claude/worktrees/signup-form/ on branch worktree-signup-form

git worktree list          # every parallel checkout you have open

# a worktree is a fresh checkout: install deps again, and list the
# gitignored files (.env and friends) you need copied into each one
echo ".claude/worktrees/" >> .gitignore
echo ".env" >> .worktreeinclude

# push first, then hand a long job to a cloud session
claude --cloud "Execute the migration plan in docs/migration-plan.md"
```
</Terminal>

`/batch <instruction>` splits one large change across five to thirty worktree-isolated subagents, each opening its own pull request. It is the fastest legitimate fan-out in the tool, and the fastest way to produce thirty PRs nobody has read.

This prompt forces the split into the open before anything spawns.

<Prompt title="Fan-out prompt" where="Claude Code · main session">
```text
Job: [one sentence].

Before you spawn anything, propose a split and show it to me. For each task:
  OBJECTIVE  one sentence: what is true when it is done
  FILES      the exact files it owns. No file may appear in two tasks.
  CHECK      the command that proves it worked, and its expected result
  BOUNDARY   what it must not touch, and what it should hand back to me
             instead of deciding on its own

Merge any two tasks that share a file or share a design decision.
If fewer than two tasks survive that rule, say so and just do the work
yourself in this session — do not spawn anything.

Then run the surviving tasks as worktree-isolated subagents, one per task,
on Sonnet. Each returns at most 15 lines: what changed, the check it ran,
and the output of that check. No narrative.

When they are all back, start a fresh subagent that wrote none of this code.
Its only job is to re-run every check and report what actually fails.
```
</Prompt>

## Where the money goes, and how to watch it go there

The [Claude Code cost docs](https://code.claude.com/docs/en/costs) put an agent team at "approximately 7x more tokens than standard sessions when teammates run in plan mode" — carry the condition with the number, because the multiplier is not fixed.

1. **Route models by role.** Expensive model plans and synthesises, cheap model does the parallel legwork — the Opus-lead, Sonnet-workers shape. Set `model: haiku` on simple subagents; name the model when you spawn teammates.
2. **Cap anything that loops.** An iteration cap in the prompt, `--max-budget-usd` on scripted runs. Unbounded loops on an API key are where surprise bills come from.
3. **Read `/usage`.** Plan bars plus an attribution breakdown: skills, subagents, plugins, MCP servers, loops. `/insights` writes an HTML report on how you work; `/context` shows what fills the current window.
4. **Know what normal is.** That same page puts enterprise use at roughly $13 per developer per active day, and under $30 per active day for 90% of users. An afternoon of fan-out that dwarfs that should have bought something you can name.

For real observability, Claude Code [exports OpenTelemetry](https://code.claude.com/docs/en/monitoring-usage): `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus an `OTEL_EXPORTER_OTLP_ENDPOINT` gives you `claude_code.token.usage`, `claude_code.cost.usage` and `claude_code.code_edit_tool.decision`. That last one, how often edits are accepted, is the number nobody looks at.

<Myth
  n={14}
  myth="More agents means more throughput."
  source="Cursor, Jan 2026"
  href="https://cursor.com/blog/scaling-agents"
>
Cursor tried it. Twenty flat peer agents coordinating through locks slowed to the throughput of two or three, because locks were held too long or never released. Optimistic concurrency failed differently: agents turned risk-averse, made small safe edits, and churned.

What worked was hierarchy: planners that spawn sub-planners, workers that grind one task with no cross-talk, a judge at the end of each cycle. Removing the integrator role removed a bottleneck. Every agent you add is another coordination surface.
</Myth>

## The rule: independent, and independently verifiable

The largest published example is Nicholas Carlini's [C compiler built by parallel Claudes](https://www.anthropic.com/engineering/building-c-compiler), February 2026: sixteen Opus 4.6 instances, each in its own Docker container with its own clone, each looping endlessly, claiming tasks through lock files. Two thousand sessions over two weeks, just under $20,000, about 100,000 lines of Rust that compiles Linux 6.9 on three architectures.

Two lessons for your laptop. The agent optimises for exactly the problem the tests define, so weak tests give a confidently wrong product ([module 10](/en/learn/test-and-quality/)) — and sixteen agents give sixteen times as much of it. Parallelism also collapsed whenever every agent hit the same giant task; the fix was splitting that task against an external oracle, not adding agents.

**Parallelise only work that is independent and independently verifiable.** Independent: separate files, no shared design decision. Independently verifiable: each slice has its own check — a test, a build, a script — that passes or fails without a human reading the diff. Work that fails either half belongs in one session, in order.

<Deeper title="A default stack you can actually run this month">
One agent in the main session. Subagents for investigation, so file reads and log dumps come back as summaries. A fresh-context reviewer on every diff you did not write.

Add parallel *writers* only when the checklist passes, with worktrees and one owner per file. Agent teams and thirty-subagent batches are the last thing you reach for.
</Deeper>
