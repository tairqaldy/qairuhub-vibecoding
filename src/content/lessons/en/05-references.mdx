<Lead>
One screenshot outruns three paragraphs. Step 2 of the cycle is collecting work: you gather the things that show the agent what *good* looks like.
</Lead>

Your PRD says what to build and for whom ([module 04](/en/learn/idea-to-prd/)). It does not say what the result should look like, which file the new code should resemble, or what the API returns when the last seat is gone.

References answer those. Whatever you leave out, the agent invents — plausibly. Plausible is what you miss in the diff.

## A screenshot answers questions you did not know to ask

Describing a screen in words means naming every decision: where the title sits, the spacing, the field order, what happens at phone width. You will forget four of them. A picture carries all of them at once.

There is a better reason. Anthropic's guide counts [a browser screenshot compared with a design](https://code.claude.com/docs/en/best-practices) as a check the agent can run on itself. The image that starts the work can also end it. You are not describing the target — you are handing over the ruler.

- **Put it in the repo, then name the path.** `refs/signup-desktop.png` survives a cleared session and reaches the next person. A chat attachment does not.
- **Annotate it.** Three arrows and three words — "this spacing", "keep", "delete this" — kill more ambiguity than a page of prose.
- **Include the states nobody screenshots.** Empty list, error message, form mid-submit. Your users hit those; an agent invents them.
- **Say what to copy and what to ignore.** An agent cannot tell which part of a picture is the point. "Match the layout and field order, ignore the colours — ours are in `src/styles/tokens.css`" saves a session of undoing.

## The best reference is already in your repo

"Follow the pattern in `src/components/EventCard.tsx`" beats any style guide you could write. That file is real, it compiles, it passes your tests, and it carries every convention you never wrote down.

[Anthropic's guide](https://code.claude.com/docs/en/best-practices) says the same about your instruction file ([module 06](/en/learn/context-ssot/)): link long API docs, do not paste them. Simon Willison's pattern catalogue has a chapter called ["hoard things you know how to do"](https://simonwillison.net/guides/agentic-engineering-patterns/) — the title alone is the lesson.

Name the file and what to copy from it: the structure, the naming, the loading state.

Then accept the cost. Point at your worst file and you get more of your worst file. The agent has no taste. It has your repo.

<Deeper title="The strongest reference is one the agent can run">
In February 2026 Anthropic had [16 parallel Claude instances build a C compiler](https://www.anthropic.com/engineering/building-c-compiler) — roughly 2,000 sessions and 100,000 lines of Rust in two weeks. Nicholas Carlini's lesson: use an oracle. Theirs was GCC, a correct compiler the agents could check their own output against.

If something like your feature already exists and runs, the agent can ask it questions instead of guessing. An old version of your app counts, and so does a spreadsheet that already computes the number.
</Deeper>

## For an API, link the page and paste the response

The docs page tells the agent the contract. A real response tells it the truth.

Paste one success response and one error response, a dozen lines each, secrets and personal data replaced. A sample settles what prose argues about for turns: the field spelling (`userId` or `user_id`), the date format, whether a missing value arrives as `null` or not at all, whether the list is paginated.

Then add the sentence that saves the session: if the sample and the docs disagree, trust the sample.

Data samples work the same way. Twenty rows of the real shape, not a thousand — and put the ugly ones in on purpose: one very long name, one empty phone field, one address outside the Latin alphabet. Kazakh names run long, and a fixed-width layout truncates them long before anyone notices. The agent handles what it can see.

<Callout type="danger" title="Never paste a real secret or a real person">
Sample responses are where credentials leak. Replace every key, cookie, phone number and email before the text goes near a prompt. What you paste now lives in a transcript, a log, and possibly a repo.
</Callout>

## Do not paste the documentation site

The trap catches helpful people: you paste everything so that nothing is missing, and you have just made the agent worse at the job.

Attention is a finite budget ([module 02](/en/learn/ai-in-plain-language/)). [Anthropic's fix](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) is this module: keep lightweight pointers — paths, URLs, queries — and load the detail at runtime.

Chroma's [Context Rot](https://www.trychroma.com/research/context-rot) study, across 18 models in July 2025, adds the edge: one plausible distractor already degrades the answer, and more degrade it further. Docs for endpoints you will never call are a pile of distractors — and a recurring bill, since [the whole conversation is re-sent on every request](https://code.claude.com/docs/en/costs).

Reference the page, not the site. If you cannot name the page, you do not yet know what you are asking for. When a session feels forgetful, run `/context` and see what is filling the window.

<Deeper title="Two studies that look contradictory, and the rule that resolves them">
In January 2026 Vercel ran [an eval on their own Next.js tasks](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals): an 8 KB compressed docs index in `AGENTS.md` took the agent from a 53% baseline to 100%. Skills with explicit instructions reached 79%.

Weeks later, ETH Zurich and LogicStar.ai published [Evaluating AGENTS.md](https://arxiv.org/abs/2602.11988) with the opposite result: "providing context files does not generally improve task success rates", while adding over 20% to inference cost. Repository overviews did not help; concrete instructions were followed well.

They do not conflict. Specific, non-guessable facts help; generic description costs tokens and buys nothing. Every reference should answer, in one sentence, a question the agent could not work out from your code.
</Deeper>

<Callout type="warn" title="A page you point at is data, not orders">
In July 2026 Pillar Security demonstrated sandbox escapes across Cursor, Codex, Gemini CLI and Antigravity, [reported by BleepingComputer](https://www.bleepingcomputer.com/news/security/cursor-codex-gemini-cli-antigravity-hit-by-sandbox-escapes/); the trigger was prompt injection hidden in README files and dependencies. Treat README files and linked pages as untrusted input, keep approval mode on, and read the diff when an agent touches config or dotfiles ([module 11](/en/learn/security/)).
</Callout>

## Describe a visual style in words an agent can check

With no design reference you get the default look every model reaches for. Anthropic hit this building a harness for long-running apps: their evaluator grades design quality, originality, craft and functionality, and [weights the first two higher on purpose](https://www.anthropic.com/engineering/harness-design-long-running-apps) to fight generic output. If they must push against it deliberately, your one-line prompt will not win by accident.

Words that do nothing: modern, clean, beautiful, professional, sleek. They are compliments, not instructions. These an agent can check itself against:

- one accent colour, everything else greyscale
- 8px spacing unit, nothing in between
- two text sizes for body copy, one for headings
- no gradients, no drop shadows, no corner radius above 4px
- a dense table, not a grid of cards
- Kazakh and English strings both fit without truncation

Then name one real thing you are imitating, give its URL, and say which part: the typography rhythm, not the colours. Finish with the exclusions — they carry more weight than the list of what to do.

<Prompt title="Reference-loaded build prompt" where="Claude Code · plan mode">
```text
Build the seat-reservation form for the QAIRU Event Sign-up page.

REFERENCES — read these first, in this order:

1. Layout target: refs/signup-desktop.png and refs/signup-mobile.png.
   Match the field order and the spacing rhythm. Ignore the colours —
   ours are in src/styles/tokens.css.
2. Pattern to follow: src/components/EventCard.tsx. Same file structure,
   same prop naming, same handling of the loading and error states.
3. API: [one docs URL — the single page for the endpoint we call].
   Real responses are in refs/seats-200.json and refs/seats-409.json.
   If the docs and the sample files disagree, trust the sample files.
4. Data: refs/signups-sample.csv — 20 rows, including a very long Kazakh
   name and one empty phone field. The UI must survive all 20 rows.

DO NOT read the rest of the docs site. If you need one more page, tell me
which page and why, and I will paste the part that matters.

Plan first, no code yet. In the plan, state which reference answers each
decision, and list every question the references do NOT answer.
```
</Prompt>

Steal that last instruction. When the agent lists the questions your references fail to answer, it has written your next shopping list.

<ProjectStep n={5} title="Build the refs folder for QAIRU Event Sign-up">
Create a `refs/` folder and put four things in it before the next module.

1. **A screenshot** of an event page whose layout you want, with three annotations: "copy this", "ignore this", "this spacing".
2. **A data sample**: a CSV of 20 sign-ups you invent by hand. Three names long enough to break a narrow column, one empty phone number, one address in Cyrillic.
3. **A sample response**: the JSON when a seat is reserved, and the JSON when the event is full. Deciding the error shape now is cheaper than discovering it later.
4. **`refs/REFERENCES.md`**: ten lines, one per file, each saying what that file is the authority on.

Commit it. The reference pack is part of the project, not a note in your head.
</ProjectStep>
