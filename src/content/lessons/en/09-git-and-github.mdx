<Lead>
A coding agent edits faster than you can read. It will get something wrong. Git decides what that costs you — and the answer is *one command*.
</Lead>

Without version control, every agent run is a one-way door. The version that worked slips away while you argue about what changed three prompts ago.

With it, a bad run is a shrug: throw it away, write a better prompt, run again.

## Five words carry the whole system

| Word | What it is |
|---|---|
| **Repo** | Your project folder plus its full history, in a hidden `.git` folder. Offline, no account needed. |
| **Commit** | One snapshot: the state of every file, plus a message explaining the change. |
| **Branch** | A parallel line of work. `main` stays untouched until you merge. |
| **Remote** | A copy of the repo on a server, usually GitHub. You push to it, you pull from it. |
| **Pull request** | A proposal to merge one branch into another. Shows which lines changed and runs checks first. |

Five commands cover most days.

<Terminal title="bash">
```bash
cd qairu-signup
git init
git status
git add .
git commit -m "chore: first working version"
git log --oneline
```
</Terminal>

`git status` is the one you run most: what changed since the last snapshot, and what goes into the next. `git add` stages files, `git commit` takes the snapshot, `git log --oneline` reads the history back.

## From your laptop to an address on the internet

Create an empty repository on GitHub — no README, no licence, you already have files. Copy the URL.

<Terminal title="bash">
```bash
git remote add origin https://github.com/YOUR-NAME/qairu-signup.git
git branch -M main
git push -u origin main
```
</Terminal>

After the first push, `git push` alone is enough. `git pull` goes the other way, bringing down commits the remote has and you do not. Run it before you start work, not after you have edited the same file. Your history now lives in two places, and a host can deploy from that URL ([module 12](/en/learn/deploy/)).

## .gitignore keeps files out of the repo

A `.gitignore` file tells git which paths to pretend it cannot see. Four lines cover a typical project:

<Terminal title=".gitignore">
```text
.env
node_modules/
dist/
.claude/worktrees/
```
</Terminal>

`.env` holds your API keys ([module 08](/en/learn/local-build/)) and must never be committed. `node_modules/` is reinstallable and enormous, `dist/` is generated, `.claude/worktrees/` holds Claude Code's parallel working copies.

<Callout type="danger" title="A committed secret does not get uncommitted">
Deleting a key from a file and committing again does not remove it. Every earlier snapshot still holds it, and if you pushed, so does someone else's server. Treat any key that reached a commit as public: issue a new one, revoke the old. Write `.gitignore` before your first commit.
</Callout>

## Write commit messages you can still read at 2 a.m.

A commit message has one job: let a future reader decide in two seconds whether this is the commit to undo. Conventional commits give it a shape — a type, an optional scope, one line of description.

<Terminal title="git log --oneline" copy={false}>
```text
feat(signup): store reservations in D1
fix(form): reject an empty email instead of saving it
test(form): cover the duplicate-email case
refactor(api): split the handler into two files
docs(readme): how to run the dev server
chore(deps): bump astro
```
</Terminal>

Six types carry almost everything: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`. Keep the first line short enough to scan, and put the *why* in the body. Then `git log --oneline` is a changelog you can revert line by line.

Anthropic's [write-up on harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) gives the agent the same habit: commit after each unit of progress, so a later session can find its way back to a state that worked.

## Undo has three shapes, and only one is safe after a push

Match the situation to the command.

| What happened | What you run |
|---|---|
| The agent changed files, nothing is committed, you want the old state | `git restore .` for tracked files |
| It also created new files you do not want | `git clean -fd` — deletes untracked files and folders |
| You want to park the mess without losing it | `git stash`, then `git stash pop` to bring it back |
| The last commit is bad and you have **not** pushed | `git reset --hard HEAD~1` — the commit is deleted |
| The bad commit is already pushed or shared | `git revert HEAD` — a new commit undoes it |

`git clean -fd` deletes untracked files permanently — git never recorded them, so nothing can be restored. Ignored files survive unless you add `-x`, so `.env` is safe. Run `git clean -nd` first: it lists what would go without touching anything.

<Compare a="git reset --hard" b="git revert">
<div slot="a">
Rewinds the branch and deletes the commit. Fine while the work is only on your laptop. After a push it is a trap: the next push demands `--force`, and forcing over a branch others have pulled is how teams lose work.
</div>
<div slot="b">
Adds a new commit that is the exact inverse of the bad one. Nothing is destroyed, and the log shows both the mistake and its undo. Safe before a push and after. Your default.
</div>
</Compare>

Revert works on any commit, not only the last: copy the short hash from `git log --oneline` and run `git revert a1b2c3d`. If later work built on it, git stops and shows you the conflict instead of guessing.

## Checkpoints are local undo. Git is permanent undo.

Claude Code has its own safety net: every prompt creates a checkpoint, and files are snapshotted before each edit. `Esc Esc` on an empty input, or `/rewind`, restores code, conversation, or just one of them. For "that last edit was wrong" it beats any git command.

The [checkpointing docs](https://code.claude.com/docs/en/checkpointing) say checkpoints are not a replacement for git. Only the 100 most recent per session are kept, and they are swept about 30 days after the session last saved one. They do not track changes from Bash commands such as `rm`, `mv` and `cp`, most subagent edits, edits made outside the session, or symlinked and hard-linked files.

<Callout type="warn" title="The failure case is exactly the uncovered one">
The run that hurts is the one where the agent shells out — moves a folder, deletes a directory, regenerates files with a script. Checkpoints do not cover that. A commit does, because it does not care who changed the file or how.
</Callout>

## Commit before you press Enter

**`git status` should say "working tree clean" before you send a prompt that will touch more than one file.** Then commit each unit of work that passes its check, before starting the next.

<StatRow>
  <Stat value="93%" label="of permission prompts users approved anyway" source="Anthropic, Mar 2026" href="https://www.anthropic.com/engineering/claude-code-auto-mode" tone="warn" />
  <Stat value="17%" label="of genuinely over-eager actions the auto-mode classifier missed" source="Anthropic, Mar 2026" href="https://www.anthropic.com/engineering/claude-code-auto-mode" tone="warn" />
</StatRow>

Approval fatigue is measured, not theoretical. When almost every prompt gets a yes, "allow" stops being a decision — and the classifier that approves on your behalf still lets 17% of over-eager actions through ([module 07](/en/learn/the-agent/)). A commit before the run never gets tired.

Small commits also make review cheap. A forty-line diff you will actually read. A two-thousand-line diff you will scroll and approve, which is a signature, not a review.

<Prompt title="Git rules for your agent" where="Claude Code · AGENTS.md or the first message of a session">
```text
Git rules for this repo:
- Before starting a task, run `git status`. If the tree is not clean, stop and tell me.
- Work on a branch named feat/<short-name> or fix/<short-name>. Never commit directly to main.
- Commit after each unit of work that passes its check. One logical change per commit.
- Message format: type(scope): what changed.
  Types: feat, fix, docs, refactor, test, chore.
- Never run `git push --force`. Never amend a commit that is already pushed.
  Never add .env or anything listed in .gitignore.
- When the task is done, show me `git log --oneline` for this branch and `git diff --stat`
  against main, then wait for my review before opening a pull request.
```
</Prompt>

## One branch per task, one pull request per review

Branch before the agent starts, not after: `git checkout -b feat/seat-counter`. If the run goes badly you delete the branch and `main` never knew. If it goes well, open a pull request — even alone. That is where you read the diff file by file, where checks run, and where a fresh agent session can review code it did not write.

Simon Willison's rule: never open a pull request containing code you have not reviewed yourself. Keep them small, with the evidence that they work. His [anti-patterns](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/) and [using git with coding agents](https://simonwillison.net/guides/agentic-engineering-patterns/using-git-with-coding-agents/) are what to read next.

<Myth
  n={9}
  myth="With agents this good, you do not need to understand code any more."
  source="Simon Willison · anti-patterns"
  href="https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/"
>
You cannot recover from what you cannot read. Every move on this page is a judgement call: which changes belonged to the task, which commit introduced the bug, is this diff the fix or a second bug. Git hands you the evidence; reading it is your job. An agent that writes code you do not understand has not removed the work — it moved it to the moment when something is already broken.
</Myth>

<Deeper title="One agent per worktree, when you start running two at once">
A worktree is a second working directory on its own branch, sharing the same repo history, so two agent sessions never overwrite each other's files: `git worktree add ../qairu-feature-a -b feature-a`, with `git worktree list` and `git worktree remove`. Claude Code wraps this as `claude --worktree feature-auth`: it creates `.claude/worktrees/feature-auth/` on a branch named `worktree-feature-auth` and removes clean worktrees on exit. A fresh checkout, so dependencies install again and ignored files such as `.env` do not come along ([worktrees docs](https://code.claude.com/docs/en/worktrees)). When to run two sessions at all is [module 14](/en/learn/multi-agent/).
</Deeper>

<Prompt title="When the agent has gone off the rails" where="Claude Code · before you undo anything">
```text
Stop. Do not change any more files.

1. Run `git status` and `git diff --stat` and show me the raw output.
2. For each changed file, tell me in one line whether it was part of the task
   I asked for, or something you decided to change on your own.
3. Do not commit, and do not run git checkout, git restore, git reset or git clean.
   I decide what gets thrown away.
```
</Prompt>

<Callout type="live" title="Do this one on stage">
Make a throwaway commit, run `git reset --hard HEAD~1` in front of the room, and show `git log` with the commit simply gone. Then make another, run `git revert HEAD`, and show the log keeping both entries. Seeing "deleted" next to "undone" is what makes people commit.
</Callout>

<ProjectStep n={9} title="Put QAIRU Event Sign-up under git, then break it on purpose">
Five moves. The last two you repeat all course.

1. In the project folder: `git init`. Open the `.gitignore` from module 8 and add `dist/` and `.claude/worktrees/` — before anything else.
2. `git add .` then `git commit -m "chore: first working version"`. Check: `git status` says clean, `git log --oneline` shows one line.
3. Create an empty repo on GitHub, then `git remote add origin` with its URL, `git branch -M main`, `git push -u origin main`. Refresh the page — your project has an address.
4. The drill. `git checkout -b feat/seat-counter`, then ask your agent to add a "12 seats left" counter to the sign-up page. When it finishes: `git add .` and `git commit -m "feat(signup): seats-left counter"`.
5. Now undo it: `git revert HEAD`. Reload the page — the counter is gone, and `git log --oneline` shows the change and its reversal. Finish with `git checkout main`. That is the move you will need on a bad day.
</ProjectStep>
