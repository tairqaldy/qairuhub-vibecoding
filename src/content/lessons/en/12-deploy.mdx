<Lead>
Your sign-up page exists on exactly one computer on Earth: yours. Close the lid and it is gone. Deploying copies it onto machines that never sleep and gives it a name people can type. On this stack that is *four commands* — plus one thing you cannot do from the terminal.
</Lead>

Working on your machine is not done. Deployed is done.

## Hosting is someone else's computer that never turns off

A host is a machine with a public address that stays on. You hand it your files; it answers when a browser asks.

Modern hosts watch your repository and deploy on every `git push`: pull the code, build it, publish it in a minute or two, with a preview URL for every branch. Nothing is uploaded by hand.

## Static or server-rendered decides everything else

**Static** means the site is built once into a folder of plain HTML, CSS and JavaScript, and that folder is copied to machines around the world. Nothing runs per visitor, which makes it the cheapest, fastest and hardest to break. This site is static: `npm run build` turns the source into `dist/`, and `dist/` *is* the website.

**Server-rendered** means a program runs for each request: it checks who you are, reads the database, calls a paid API. That code runs out of the visitor's sight, the only place a secret can live. Two shapes: one long-running server, or small serverless functions (Cloudflare Workers, Vercel Functions) that wake per request and sleep again.

Keep as much static as you can; push the dynamic part into the smallest possible function. A static page costs you nothing. A function spends budget every time someone loads it — [Cloudflare's free Workers tier](https://developers.cloudflare.com/workers/platform/pricing/) allows 100,000 requests a day and 10 ms of CPU per invocation, while Pages lists no bandwidth cap at all for static assets.

<Deeper title="Where a reserved seat actually gets stored">
A sign-up form needs a database. Each sensible free option has a catch.

- **Cloudflare D1** (SQLite): 5M rows read and 100k rows written per day, 5 GB total. Same account as your Pages project, no card.
- **Neon** (Postgres): 0.5 GB storage per project, 100 CU-hours per project per month, mandatory scale-to-zero after 5 minutes — which means the first query after a quiet hour is slow.
- **Supabase** (Postgres plus auth): 500 MB database, 50,000 monthly active users, 2 active projects — and the project is **paused after one week of inactivity**, exactly how long a demo sits between the workshop and the follow-up.

Sources: [Cloudflare](https://developers.cloudflare.com/workers/platform/pricing/), [Neon](https://neon.com/pricing), [Supabase](https://supabase.com/pricing).
</Deeper>

## A domain is a rented name, and DNS is the phone book

Your site has an address the moment it deploys — something like `qairu-event.pages.dev`. A custom domain is a nicer name pointed at the same place.

DNS translates a name into the address of the machine that answers for it. Attaching a domain means adding a record — usually a **CNAME**: "this name means that server". Your host then issues the SSL certificate that turns `http://` into `https://`, free and automatic.

DNS answers are cached worldwide, so a change takes minutes to hours to reach everyone. If the site works for you and not for your friend, you are looking at a cached old record, not a broken deploy. Wait before you debug.

## Secrets belong on the host, never in the repo and never in the browser

An environment variable is a named value handed to your program when it starts — an API key, a database address, `NODE_ENV=production`. It lives outside the code, so the same code behaves differently on your laptop and on the server.

A secret can live in exactly three places. Only one is correct:

- **In a `.env` file on your laptop.** Fine, as long as `.env` is in `.gitignore` before your first commit.
- **In the host's dashboard**, as an environment variable your server code reads. This is production.
- **In the frontend.** Never. Anything the browser downloads is public; developer tools show it in seconds.

First deploys die between the first place and the second. Your `.env` never leaves your laptop, so nothing in it exists on the host until you type it there. Go key by key through `.env` and add each one in the host's dashboard. A page that works locally and errors in production usually has one variable in only one of the two places.

The `.env` deny rule from [module 08](/en/learn/local-build/) helps, but it blocks Claude's file tools, not a script that opens the file itself ([permissions docs](https://code.claude.com/docs/en/permissions)).

## Every branch gets its own URL, so break things where nobody is watching

A preview deploy is a full copy of your site built from one branch, at its own unlisted address. Send that link instead of a screenshot. On Netlify previews are not metered at all — only production deploys cost credits, so a preview is the cheapest place to be wrong.

Previews also catch the classic "it works on my machine" failure: your host builds on Linux, and Linux cares about capital letters in filenames. `Header.astro` imported as `header.astro` works all day on your laptop and fails in the build log. Read the log; it names the file.

## The four commands that ship it, and the click at the end

<Steps>

<Step title="Prove it builds before anyone else sees it">
The repo behind this site bundles its checks into one script: translations, types, build, links, in that order, stopping at the first failure.

<Terminal title="bash">

```bash
npm run verify
```

</Terminal>
</Step>

<Step title="Build the folder that is the website">
`npm run verify` already ran this as its third step. Run it alone anyway and open `dist/`: plain HTML, CSS and JavaScript. A static site is just a folder.

<Terminal title="bash">

```bash
npm run build
```

</Terminal>
</Step>

<Step title="Push, which is your backup and your trigger">
Your commits go to GitHub: the history you roll back to, and on a repo wired to CI, the button that starts everything else.

<Terminal title="bash">

```bash
git push origin main
```

</Terminal>
</Step>

<Step title="Publish the folder to the edge">
Wrangler is Cloudflare's CLI. It uploads `dist/` and hands you a live URL on `pages.dev`, over HTTPS, at no cost. `qairu-event` is the Pages project name — use your own, and the URL you get back is that name plus `.pages.dev`.

<Terminal title="bash">

```bash
npx wrangler pages deploy dist --project-name=qairu-event
```

</Terminal>
</Step>

<Step title="Attach the domain — and this one is not a command">
You cannot finish this step from the terminal. Open the Cloudflare dashboard, find your Pages project, go to **Custom domains**, add the name. Cloudflare creates the CNAME record and the SSL certificate. Then you wait for DNS.

Deploy guides skip this step. Your agent will skip it too, then tell you the site is live when it is only on `pages.dev`.
</Step>

</Steps>

## One GitHub Action, start to finish

Continuous integration is the same commands, run by someone else's machine on every push, so you cannot forget them. It lives in your repo as a file:

<Terminal title=".github/workflows/deploy.yml">

```yaml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  ship:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm run verify
      - run: npx wrangler pages deploy dist --project-name=qairu-event
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          CLOUDFLARE_ACCOUNT_ID: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}
```

</Terminal>

Read it top to bottom: on a push to `main`, rent a Linux machine, check out the code, install Node 20 and the exact dependencies from the lock file, run the checks — which already produce `dist/` — then publish. The token is never in the file: GitHub stores it encrypted and substitutes it at run time. Secrets live on the host, and a build machine is a host.

GitHub Free gives 2,000 Actions minutes a month on private repositories, and standard runners are **free on public repositories**. A public repo plus Cloudflare Pages is a complete pipeline for zero. ([GitHub billing docs](https://docs.github.com/en/billing/concepts/product-billing/github-actions))

<Callout type="warn" title="The two lines that go stale">
Everything in that file is stable except the two `uses:` version pins. Actions get new major versions and old ones stop being supported. When a workflow that ran for months suddenly fails on a `uses:` line, check the pin first, and say so when you paste the log to your agent.
</Callout>

## Rollback is a skill you practise on a quiet Tuesday

Your agent's undo does not reach production. Claude Code checkpoints cover file edits and explicitly not remote side effects — database writes, pushes, deploys. `/rewind` puts your source back while the broken version stays live. ([Checkpointing docs](https://code.claude.com/docs/en/checkpointing))

So rollback is a git operation followed by a deploy:

<Terminal title="bash">

```bash
git log --oneline -5
git revert --no-edit <commit-hash>
git push origin main
npm run build
npx wrangler pages deploy dist --project-name=qairu-event
```

</Terminal>

Small commits are what make this fast. If one commit holds an agent's whole afternoon across forty files, reverting throws the good work out with the bad ([module 09](/en/learn/git-and-github/)).

Do the part almost nobody does: run that sequence today, while the site is fine. A rollback you have never tested is a plan, not a safety net.
