## Logs are all you get, and they expire

On your laptop a crash is a red line in the terminal. In production you cannot attach a debugger to a stranger's phone in Shymkent at 23:40. All you get is what your program wrote down while it ran: timestamped lines about requests, errors and values you chose to print.

The free tier you picked in [module 12](/en/learn/deploy/) has a catch. Those lines do not wait for you.

A user hits an error on Friday night. You open the dashboard on Sunday. On one of those hosts the evidence is already gone.

## Four streams, four questions

People say "check the logs" as if there were one thing. There are four.

| Stream | The question it answers | Where it lives |
| --- | --- | --- |
| Logs | What happened, in order, at what time? | Your host's dashboard, by default |
| Errors | What broke, how often, for how many people? | An error tracker you wire up yourself |
| Traces | Which step inside one request was slow? | A tracing backend, usually the same tool |
| Analytics | What did people actually do — and give up on? | An analytics tool you add to the page |

Logs are free and already on; the rest you add when the project has real users.

## Read a stack trace in three moves

A stack trace looks like punishment. It is the most structured message your program will ever send you.

<Terminal title="production log · POST /api/reserve">

```text
2026-09-21T18:04:11.382Z  ERROR  POST /api/reserve  500  req_8f2ac1
TypeError: Cannot read properties of undefined (reading 'trim')
    at normalizeEmail (/var/task/src/lib/signup.js:42:21)
    at reserveSeat (/var/task/src/api/reserve.js:17:19)
    at async handler (/var/task/src/api/reserve.js:8:5)
```

</Terminal>

1. **The first line is the receipt.** Time, route, status code, request id. `500` means your server broke, not the user. Keep that request id — it finds every other log line from the same visit.
2. **The second line is the actual bug.** `TypeError` is the kind; the words after the colon are the sentence that matters. Something was `undefined` and the code called `.trim()` on it anyway.
3. **The lines below are the call chain, newest first.** Skip every frame inside `node_modules` or the platform's own runtime. The first frame in a file *you* wrote is where you look: `src/lib/signup.js`, line 42.

Thirty seconds of reading and you have a hypothesis: a request reached `normalizeEmail` with no email field. You have not opened the editor yet.

## Keep the error where you can find it tomorrow

Your host's log stream is a firehose that forgets. An error tracker is the opposite: your app reports each crash, and it keeps the trace, groups duplicates, counts how many people hit each one, and pings you when a new one appears. Sentry is one such tool; PostHog does the same job for the analytics row above.

Both have a free tier; check the current limits on their own pricing pages, not on this one. The vendor matters less than the rule: the error must land somewhere that keeps it and can interrupt you.

<Callout type="tip" title="Before you wire a dashboard into your agent">
Claude Code reaches an outside service two ways: an MCP server, or that service's own command-line tool. CLI tools such as `gh` and `sentry-cli` are the most context-efficient integrations; the cost guide says to prefer them over MCP servers and to switch off unused servers with `/mcp`. Start with copy-paste. Wire something up when you catch yourself opening the same dashboard five times a day. ([Claude Code docs on costs](https://code.claude.com/docs/en/costs))
</Callout>

## Measure four numbers, not forty

Analytics dashboards are built to make you feel something. Resist. There is one honest test for any metric: **if this number moved tomorrow, what would I do differently?** No answer means do not track it.

For QAIRU Event Sign-up: how many opened the page, how many started the form, how many finished and got a seat, and how many errors happened in the same window.

The gap between the second and third number is your whole product problem, stated as one subtraction. Total visits, likes, "engagement" — those rise whether or not your app works, so they teach nothing.

<Callout type="warn" title="Logs are a database you forgot you built">
Never write an email address, a phone number, an IIN, a password or an API token into a log line or an analytics event. You will paste that log into an agent and a support chat, and log stores are rarely protected the way your database is. Log the request id and the shape of the failure, not the human it happened to.
</Callout>

## Paste the whole thing, not your summary

Paste the exact error text and the log lines around it. Your summary is not a shortcut — it is lossy compression of your only evidence, done by the person who does not yet understand the bug.

<Prompt title="Debug from a production error" where="Claude Code · after a real 500">

```text
Production bug on QAIRU Event Sign-up.

What the user sees: [exact words on screen] and no seat is reserved.
Expected: the seat is reserved and a confirmation appears.
Where: [route or page]. First seen: [time]. How often: [count in the last hour].

Full log entry, unedited — assume nothing I have not pasted:
[paste the WHOLE stack trace, every frame, plus 5 log lines before and after]

The code the trace points at, pasted whole:
[paste each file the trace names, or the surrounding 40 lines if it is long]

Process, in this order:
1. Explain what this trace says, line by line, before you change anything.
   Tell me which frame is the symptom and which is the cause.
2. Reproduce it. Write a failing test that produces this exact error.
   Show me the failure output.
3. Fix it with the smallest change. Do not hide the symptom: no try/catch
   that swallows it, no skipped, loosened or deleted test.
4. Run the new test and the related suite. Show me the commands and the output.
5. Tell me where the same mistake likely exists elsewhere. List the places.
   Do not fix them yet.

If the log is not enough to be sure of the cause, say so and tell me exactly
what to log next — then stop. Do not guess.
```

</Prompt>

That last instruction is not politeness. A confident agent with a thin bug report writes a confident fix for a bug you do not have.

<Callout type="danger" title="The three signs the agent is faking green">
Kent Beck named them in June 2025: looping, features nobody asked for, and cheating — disabling or deleting tests to reach green ([module 10](/en/learn/test-and-quality/)). On a production bug the cheat is usually a `try/catch` that swallows the error. Your users still fail. You just stop hearing about it. ([Kent Beck, 25 Jun 2025](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes))
</Callout>

<Deeper title="What a trace is, and how to watch the agent itself">
A trace follows one request through every step it touched — handler, database query, external API — timing each. Logs say *what happened*; a trace says *where the four seconds went*. You want one the first time someone says "it works, it is just slow".

Claude Code can be watched the same way. `CLAUDE_CODE_ENABLE_TELEMETRY=1` plus OpenTelemetry exporters sends metrics and events — sessions, token usage, cost, lines of code, commits, tool decisions, API errors — to any OTel backend. That is team-scale tooling; alone, `/usage`, `/insights`, `/context` and the transcript are enough. ([Claude Code monitoring docs](https://code.claude.com/docs/en/monitoring-usage))
</Deeper>

## Every bug becomes a test, every complaint a spec line

An error that gets fixed and forgotten comes back. Each incident has to leave something behind:

- **A failing test that now passes.** That is step 2 of the prompt above. It joins the suite from [module 10](/en/learn/test-and-quality/) and guards that line forever.
- **A line in your context file.** If you had to tell the agent something twice, it belongs in `AGENTS.md`.
- **A saved case.** Anthropic's guidance on evals is to start from real failures: build a suite of 20 to 50 tasks that actually went wrong, then re-run it after you change a prompt, a skill, your context file or the model. Ten real ones in a folder, re-run on purpose, already beat remembering. ([Anthropic, 9 Jan 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))

Not all feedback is an error. Someone messages you: "I could not tell if it worked, so I pressed it four times." No log line contains that sentence, and it is the most valuable input you will get all week. Four duplicate reservations is the data problem. The missing confirmation state is the product problem underneath.

That goes into the PRD as a user story with an acceptance check, and the cycle restarts at step 1: [Idea → Product](/en/learn/idea-to-prd/) — this time with a requirement from a real person.

<ProjectStep n={13} title="Read your first production log">
Not a screenshot of someone else's log. Yours.

1. Open your host's dashboard and find the logs view for your sign-up project.
2. On your phone, open the live URL and submit the form once, normally.
3. Find that exact request in the logs. Say out loud: the time, the route, the status code.
4. Break it on purpose — a field left empty, or 500 characters in the name box. Find the failure.
5. Copy the **entire** entry — every frame, plus the lines around it — into `incidents/01.md`, with one sentence at the top saying how you caused it.
6. Run the debug prompt from this module against that file. Keep the failing test it writes. Ship the fix.

**Done when** you can explain the first two lines of a real error from your project without guessing, and the test that proves the fix is committed.
</ProjectStep>
