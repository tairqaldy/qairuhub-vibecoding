<Lead>
Сен оқып отырған сайт бір түнде жазылды. Зерттеу агенттері дереккөздерді жинап, әрқайсысына сілтеме қойды, факт тексеретін агент соларды *сындырып* көрді, мазмұн агенттері модульдерді жазды. Бір адам бағыт беріп, нәтижені тексерді. Мұнда сиқыр жоқ — бұл жай ғана harness (агент түнде сүйенетін тірек жүйе), оны сен де осы аптада құра аласың.
</Lead>

Түнгі жұмыс — жай ғана ұзынырақ промпт емес. Түнгі 03:00-де агент тығырыққа тіреледі, ал жауап беретін адам ұйықтап жатады. Сондықтан бәрі сенің оған алдын ала не қалдырғаныңа байланысты.

## Сол түні шын мәнінде не істелді

<Story title="Бір адам, бір топ агент" date="21 Sep 2026" place="Астана">
Үш ауысым. **Зерттеу агенттері** ұзын Markdown файлдарын жазды: ондағы әр тұжырымның қасында дереккөз сілтемесі және `[V]` не `UNVERIFIED` белгісі тұрды. Одан кейін **факт тексеретін агент** слайдқа шығу ықтималдығы ең жоғары тұжырымдарды — сандарды, күндерді, дәйексөздерді, бағаларды, пәрмендерді — бөліп алды да, әрқайсысының бастапқы дереккөзін ашып, оларды теріске шығаруға тырысты. Ол өз командасын түзетті: бес жолдық агент циклі туралы әйгілі әңгіме мүлде басқа құралға қатысты болып шықты, ал жиі қайталанатын `rm -rf ~` оқиғасы GitHub-тағы бір issue мәтінінің еркін мазмұндамасы екен — сол мәтінде мүлде басқа нәрсе айтылған. Екі түзету де файлдарда, белгісімен бірге тұр. Тек содан кейін ғана **мазмұн агенттері** сабақтарды жазды: оларға сол файлдардан басқа ештеңе пайдалануға рұқсат етілмеді.
</Story>

Мәселе агенттердің сайт жаза алатынында емес. Мәселе — бұл жұмыстың өз қателерін сахнада емес, түнгі 02:00-де бетке шығаратындай етіп құрылғанында.

## Жоспарлау режимі — бірінші қақпа, формальдылық емес

Сен оқып шыққан жазбаша жоспар болмайынша, ешқандай автономды жұмыс басталмайды. [Жоспарлау режиміне](https://code.claude.com/docs/en/permission-modes) `Shift+Tab` арқылы кір немесе бірден `claude --permission-mode plan` деп баста. `Ctrl+G` жоспарды редакторда ашады — мақұлдамай тұрып қайта жазып шығуға болады. Осыны пайдалан. Түнгі 03:00-де бөлмеде қалған жалғыз нұсқау — сол жоспар, ал үстірт қарап шыққан жоспар — оқылған жоспар емес.

Қараусыз жұмыс істейтін репозиторийде оны әдепкі режим қыл:

```json
{ "permissions": { "defaultMode": "plan" } }
```

Цикл мынадай: Explore → Plan → Code → Commit. [Құжаттамада](https://code.claude.com/docs/en/best-practices) diff-ті бір сөйлеммен сипаттай алатын жағдайда жоспарлауды өткізіп жіберуге болады делінген — түнгі жұмыста ондай жағдай ешқашан болмайды.

## Қоршау: allow, ask және жеңіп шығатын deny ережелері

Рұқсаттар `.claude/settings.json` файлында (репозиторийді клондаған әркімге ортақ) немесе `.claude/settings.local.json` файлында (тек сенде) тұрады. [Тексеру реті](https://code.claude.com/docs/en/permissions) мынадай: **deny → ask → allow, бірінші сәйкестік жеңеді, нақтылық рөл ойнамайды**.

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "defaultMode": "plan",
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run build)",
      "Bash(npm run test *)",
      "Bash(git add *)",
      "Bash(git commit *)",
      "Bash(git status *)",
      "Bash(git diff *)"
    ],
    "ask": ["Bash(git push *)"],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(~/.ssh/**)",
      "Read(~/.aws/**)"
    ]
  }
}
```

Көбіне сүріндіретін төрт нәрсе:

- `*` таңбасын ішкі пәрменнен **кейін** қой: `Bash(git log *)`, ешқашан `Bash(git *)` емес. Бос орынға да мән бер — `Bash(git diff*)` деген жазу `git diff-index` пәрменіне де сәйкес келеді.
- Bash ережелері бағдарламаның өзіне емес, **пәрмен мәтініне** қарап сәйкестендіріледі. `Bash(rm *)` деген ереже `/bin/rm` шақыруын тоқтатпайды.
- Файлдар үшін тек `Read(path)` және `Edit(path)` ережелері қаралады. `Write(...)` жолы бар ереже формат тұрғысынан қабылданады, бірақ ешқашан тексерілмейді.
- `Read` бойынша тыйым сол жерде Edit пен Write әрекетін де бұғаттайды әрі Bash-тегі `cat`, `head`, `sed` пәрмендерін қамтиды — бірақ файлды өзі ашатын скриптті қамтымайды.

<Callout type="warn" title="Бұл қоршау не және не емес">
Allow мен deny тізімдері — ыңғайлылық, қауіпсіздік шекарасы емес. Нағыз шекара керек болса, операциялық жүйе деңгейіндегі sandbox немесе `PreToolUse` hook қажет — және құпия деректер сен жұмысты бастаған қалтадан қол жетпейтін жерде жатуы керек.
</Callout>

## Рұқсаттарды өшіретін жалауша неге дұрыс жауап емес

`--dangerously-skip-permissions` барлық сұрауды өшіреді, ал құжаттама бұл жалаушаны (flag) тек оқшауланған контейнерлер мен виртуалды машиналармен шектейді. Одан да өткір себеп бар: 2025 жылғы тамызда болған [Nx жеткізу тізбегіне шабуылда](https://www.wiz.io/blog/s1ngularity-supply-chain-attack) зиянды post-install скрипті машинада бұрыннан тұрған ЖИ CLI құралдарын іздеп тапты да, **оларға `--dangerously-skip-permissions`, `--yolo` және `--trust-all-tools` жалаушаларымен промпт беріп**, өзіне құпия деректерді жинатты. Мыңнан астам GitHub токені және шамамен 20 000 файл сыртқа шықты. Сенің кедергіңді алып тастайтын жалауша оны сенің атыңнан жұмыс істейтін кез келген басқа нәрсе үшін де алып тастайды.

Оның орнына мыналарды осы ретпен қолдан:

1. **Auto режимі** — әр әрекетті сенің орныңа классификатор қарайды, әрі ол Pro, Max және Team жоспарларында әдепкі бастапқы режим болып тұр. [Anthropic-тің осы туралы жазбасында](https://www.anthropic.com/engineering/claude-code-auto-mode) себебі де, шынайы шегі де айтылған: пайдаланушылар рұқсат сұрауларының шамамен 93%-ын бәрібір мақұлдайды екен, ал жүйенің жалған оң нәтижесі — 0,4%, **шынымен шектен шыққан әрекеттердегі жалған теріс нәтижесі — 17%**. Бұл — қауіпсіздік белдігі, sandbox емес.
2. **`/sandbox`** — Bash үшін операциялық жүйе деңгейіндегі файлдық жүйе мен желі оқшаулауы. Anthropic өзінің ішкі тәжірибесі туралы былай дейді: "sandboxing safely reduces permission prompts by 84%" ([2025 жылғы қазан](https://www.anthropic.com/engineering/claude-code-sandboxing)) — яғни sandbox рұқсат сұрауларын қауіпсіз түрде 84%-ға азайтады. Deny тізімінен айырмашылығы — бұл нағыз шекара. macOS, Linux және WSL2-де жұмыс істейді, **таза Windows-та жоқ**, сондықтан Windows-пен отырған студент қараусыз жұмысты WSL2 ішінде жүргізеді.
3. **Контейнер немесе виртуалды машина** — үй қалтаңа бағыттағың келмейтін кез келген іс үшін.

## Harness: жұмыс ештеңе істемей тұрып нені оқиды

Ұзақ жұмыс — бұл көп қысқа сеанс, әрқайсысы алдыңғысын мүлде есіне сақтамай басталады, сондықтан жалғастықтың жалғыз көзі — дискіде жатқан нәрсе. Anthropic-тің [harness бойынша жұмысында](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) бір рет қана орындалатын **инициализатор** бар — орнату скрипті, үлгерім файлы, мүмкіндіктер тізімі, бірінші commit — және әр келесі сеанста **бір ғана** мүмкіндікті ұқыпты аяқтайтын **кодтаушы агент** бар. Бір шешімді сөзбе-сөз көшіріп ал: мүмкіндіктер тізімі JSON форматында, себебі модельдер JSON-ды Markdown-ға қарағанда жеңіл-желпі қайта жазып жібермейді.

Репозиторий түбірінде үш файл жатады. `PROGRESS.md` — тек соңына қосылатын журнал: әр сеанс өзінен кейін бір блок қалдырады (не өзгерді, қай жерде, қалай тексерілді, келесі сеанс нені білуі керек). `BLOCKERS.md` — бос тұрғаны жақсы: бір нәрсеге екі рет сәтсіз талпынсаң, үшінші рет тырыспай, осында жазып қоясың. `TODO.json` — жұмыстың өзі объект түрінде: әрқайсысында id, тақырып және `done: false` тұрады, ал тексеру шынымен өткеннен кейін ғана `true` болады. Файлдардың пішімі мынадай:

```text
PROGRESS.md    append-only. One block per session: what changed, where,
               how it was verified, what the next session must know.
BLOCKERS.md    empty is the good state. Two failed attempts at the same
               thing → write it here, move on. Never a third attempt.
TODO.json      the work as objects with an id, a title and done: false.
               Flipped to true only after the check actually passed.
```

Осы рәсімді промптқа сөзбе-сөз жаз: сол үш файлды және `git log` шығысының соңғы жолдарын оқы, орнату скриптін іске қос, қолданбаның әлі жұмыс істеп тұрғанына көз жеткіз, аяқталмаған **бір** тармақты таңда, жүзеге асыр, тексер, commit жаса, PROGRESS.md файлына жаз, тоқта.

<Deeper title="Harness-тің әр бөлігі — модель не істей алмайтыны туралы бәс">
Anthropic-тің [2026 жылғы наурыздағы жалғасында](https://www.anthropic.com/engineering/harness-design-long-running-apps) өз командасына төрт ай бұрын керек болған механизм лақтырылып тасталды. Sonnet 4.5 контекст шегіне жақындағанда жұмысты ертерек аяқтап қоюға бейім еді, сондықтан harness ішінде спринт келісімдері мен мәжбүрлі контекст тазалау болатын. Opus 4.6-да бұл мінез көбіне жоғалды да, спринт құрылымы алынып тасталды. Әр жаңа модель шыққан сайын өз тіреуіңді қайта сынап көр де, орнын ақтамайтынын жойып отыр.
</Deeper>

## Жұмыс дауласа алмайтын қақпалар

Anthropic-тің [үздік тәжірибелер нұсқаулығының](https://code.claude.com/docs/en/best-practices) бірінші бөлімі агентке өз жұмысын тексеретін жол беру туралы: іске қосылатын тексеру болмаса, агенттің жалғыз белгісі — «дайын сияқты» деген сезім, ал тест жинағының рөлін сен атқарасың. Күш-жігері арта беретін төрт қақпа:

- Тексеруді промптта сұра да, дәлел талап ет — пәрменнің өзі және оның шығысы, құр сөз емес.
- [`/goal`](https://code.claude.com/docs/en/goal) және оған қоса бір шарт: шағын әрі жылдам модель әр қадамда жазбаны қайта оқып, баға береді. Ол құрал іске қоса алмайды, сондықтан шартты агенттің өз шығысы дәлелдейтіндей етіп жаз — «`npm test` 0 кодымен аяқталады» — және «немесе 20 қадамнан кейін тоқта» дегенмен шектеп қой.
- **Stop hook**: сенің скриптің тексеру өтпейінше қадамның аяқталуын бұғаттайды. (Қатарынан сегіз рет бұғаттағаннан кейін Claude Code оны елемей өтеді, сондықтан ол сәтті аяқтала алатындай болуы керек.)
- **Тексеруші субагент** — таза контексте отырып, нәтижені теріске шығарудан басқа ешқандай міндеті жоқ агент.

Бір скрипт, және оның шығу коды — бүкіл келісім. Әр жолы — сен `package.json` файлында өзің анықтайтын скрипт:

<Terminal title="verify.sh">
```bash
#!/usr/bin/env bash
# The run's referee. Non-zero anywhere means "not done".
set -euo pipefail

npm run typecheck      # the types still line up
npm run build          # the thing actually builds
npm test               # the behaviour you asked for still holds
npm run check:links    # no dead internal links in the built output
```
</Terminal>

Сол шығысты агентке арнап жаз: stdout-қа аз нәрсе, егжей-тегжейі журнал файлына, әр сәтсіздікке `grep` таба алатын бір жол. Бұл тәсіл [он алты Claude данасымен параллель C компиляторын жазған](https://www.anthropic.com/engineering/building-c-compiler) жобадан шыққан, ал сол жобаның осы жердегі ең маңызды ескертуі мынадай — **агент сенің тестерің қандай мәселе қойса, дәл соны шешеді**. Әлсіз тест — сенімді түрде жазылған, бірақ мүлде басқа мәселені шешетін код.

[Kent Beck-тің](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes) айтуынша, жұмыстың жолдан шыққанының үш белгісі бар: цикл айналады; ешкім сұрамаған функцияны қосады; жасыл нәтиже алу үшін тестерді өшіреді. Промптқа «тестті ешқашан өшірме, өткізіп жіберме, жойма» деп жаз да, тест саны азайса, қақпаны құлат.

## Шағын commit — қалпына келудің өлшем бірлігі

Әр аяқталған бөліктен кейін commit жаса, әрі хабарда сол бөліктің атын жаз. Түнгі 03:00-дегі сеанстың сенсіз-ақ жұмыс істейтін күйге орала алатын жалғыз тетігі — осы.

Checkpoint мұны алмастырмайды. Claude Code әр өңдеудің алдында [файлдардың суретін түсіреді](https://code.claude.com/docs/en/checkpointing), бірақ бір сеанста ең соңғы 100 суретті ғана сақтайды әрі Bash пәрмендері (`rm`, `mv`, `cp`) жасаған өзгерістерді және субагент өңдеулерінің көбін **бақыламайды**. Checkpoint — жергілікті болдырмау, ал git — тұрақты болдырмау. Тармақта жұмыс істе, және Simon Willison сипаттаған [анти-үлгіні](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/) байыппен қабылда: өзің оқып шықпаған pull request-ті ешқашан ашпа.

Мұны екі оқиға нақтылай түседі. Amazon-да инженерлер агентке бір мәселені түзетуге рұқсат берді, ал [ол жұмыс істеп тұрған ортаның бір бөлігін жойып, қайта жасап шықты](https://incidentdatabase.ai/cite/1442/); бір аймақта Cost Explorer шамамен он үш сағат бойы істемей тұрды. Бұл нұсқа Financial Times-тен алынған, ал Amazon кінәні ЖИ-ге емес, дұрыс бапталмаған қол жеткізу параметрлеріне артады — бірақ екі баяндама да тетік жағынан бір нәрсені айтады. Агент адамның кең рұқсаттарын мұра етіп алды.

Қараусыз жұмысқа тән тағы екі тұзақ бар. [`--bare` жалаушасысыз `claude -p`](https://code.claude.com/docs/en/headless) сол репозиторийдің hook-тарын және `.mcp.json` серверлерін **сенім сұрайтын терезесіз** іске қосады — сондықтан headless жұмысты өзің оқып шықпаған репозиторийге ешқашан бағыттама. Ал ноутбугіңде `aws`, `gcloud` немесе `vercel` CLI құралы қай аккаунтқа кіріп тұрса, агент соны мұра етіп алады.

## Vibe coder-ден агенттік инженерге дейін

Бұл жұмыстың кәсіби атауын бірінші акт берген еді: агенттік инженерия — Karpathy мен Willison сияқты адамдар қолданатын термин. Willison [берген анықтама](https://simonwillison.net/guides/agentic-engineering-patterns/what-is-agentic-engineering/) ең қарапайымы: код жаза да, іске қоса да алатын агенттермен бағдарламалық жасақтама құру — ал «vibe coding» деген сөзді ол тексерілмей қалған прототип нәтижесіне ғана қалдырады. Жұмыстың өзі жылжыды. Сен кодты теріп отырған жоқсың, бірақ оны елемей де отырған жоқсың. Сен спецификацияны жазасың, қоршауды таңдайсың, қақпаны құрасың, diff-ті оқисың және өзің ұйықтап жатқанда машинаға неге рұқсат бар екенін шешесің. Бұл шешімдер автоматтандырылмайды, себебі әрқайсысы — нақты дүниедегі салдар туралы, ал агент дәл соны көрмейді.

Чат терезесінен агенттерге дейінгі өз жолы: алдымен бұрын өзі істеп шыққан жұмысты агентпен қайталап көреді, содан соң оңай әрі күмәнсіз тапсырмаларды соған береді, ал ең бастысы — harness-ті инженер сияқты құрады: агент жіберген әр қате құралға, құжатқа немесе тексеруге айналады, сөйтіп сол қате екінші рет қайталанбайды. Енді нені құрасың:

- **Өзің апта сайын қолданатын нәрсе.** Адам тек өзіне керек нәрсені ғана күтіп ұстайды.
- **Қайталауға келетін қақпа.** Қолмен істейтін тексеруіңді агент іске қоса алатын скриптке айналдыр. Бұл — айдағы ең пайдалы сағат.
- **Шағын бағалау жиыны.** Сәтсіз аяқталған 10–20 нақты тапсырманы сақтап қой да, `CLAUDE.md` файлын, skill-ді немесе модельді өзгерткен сайын қайта жүргіз. Болжаудан осылай құтыласың.

Әрі қарай оқуға: Simon Willison жазған [Agentic Engineering Patterns](https://simonwillison.net/guides/agentic-engineering-patterns/), ал агентті жүргізіп қана қоймай, өзің құрғың келсе — [12-Factor Agents](https://github.com/humanlayer/12-factor-agents).

2. **Осы аптада, бір кеш.** `SPEC.md`, `TODO.json`, `PROGRESS.md` және `BLOCKERS.md` файлдарын жаз, басты промптты `PROMPT.md` файлына қой, итерация шегін орнат та, өзің бөлмеде отырып, тармақта екі сағаттық бақылаудағы бір жұмыс жүргіз. Біріктірер алдында әр commit-ті оқып шық.
3. **Апта бітпей тұрып жариялап үлгер.** Deploy жаса да, сілтеме мен `PROGRESS.md` файлыңды QairuHub-тың Telegram арнасына — [t.me/qairuhub](https://t.me/qairuhub) — жаз. Ондағы біреу сен байқамаған қатені табады, ал жариялаудың бүкіл мәні сонда. Содан кейін келесі жобаңды [qairuhub.com](https://qairuhub.com) сайтынан таңда.

Сен курсты аяқтадың. Енді идеяны алып, оған спецификация жаза аласың, агентті қоршауға отырғызып, жұмысын дәлелдеуге мәжбүрлей аласың, нәтижені нағыз URL-ге шығара аласың және оны түнге қалдырып кетуден қорықпайсың.
