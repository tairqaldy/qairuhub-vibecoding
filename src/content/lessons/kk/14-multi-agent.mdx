<Lead>
Anthropic-тің зерттеу жүйесі жетекші agent-ті іске қосады, ол жұмысты subagent-терге таратады. Компанияның ішкі бағалауында бұл жүйе жалғыз agent-тен айтарлықтай озып шықты. Сонымен бірге ол кәдімгі чаттан шамамен он бес есе көп token жейді. Бүкіл модульдің мәні — дәл осы екі сан: көп agent — *тегін жылдамдық* емес, ол — айырбас.
</Lead>

Осы уақытқа дейін жасағаныңның бәрі бір agent, бір сеанс, бір терминалмен бітті. Жұмыстың көбіне дұрыс пішін әлі де сол. Ал демалыс күніңді ең жылдам күйдіретін тәсіл — біреуі-ақ бітіретін тапсырмаға бүтін бір флот agent шақыру. Бұл модуль — сол ерекше жағдайлар туралы: олар қандай, қанша тұрады және бүгін кешке соның бірін қалай іске қосуға болады.

## Алдымен бұл саған керек емес деп есепте

Нақтырақ жазылған prompt, `/clear` пәрмені, шынымен оқып шыққан жоспар — бұлар тегін. ## Бөлудің үш дұрыс себебі және бір нашар тәсілі

2026 ж. қаңтардағы жазба екінші agent өз ақысын ақтайтын үш жағдайды атайды. **Контексті қорғау**: қосымша жұмыс негізгі терезеңді толтырып тастар еді, сондықтан ол басқа біреудің терезесінде жүреді. **Қатарластыру**: бөліктер шынымен бір-біріне тәуелсіз. **Мамандандыру**: тар құрал жиыны, тар prompt немесе тар сала жалпы маманнан күштірек. Сол жазба сәтсіз бөліністі де атайды — көпшілік дәл осы жерде қателеседі.

## Бес пішін және Anthropic шынымен шығарғаны

Терминдер Erik Schluntz пен Barry Zhang жазған [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) («Тиімді agent-тер құру») мақаласынан алынды, 2024 ж. желтоқсан. Бес үлгі — үшеуін сен атын білмей-ақ қолданып та қойдың — және уақыт сынынан өткен бір әдепкі кеңес: ең қарапайымынан баста, күрделілікті нәтижені өлшеуге болатындай жақсартқанда ғана қос.

| Пішін | Не екені | Қай жерде кездестірдің |
| --- | --- | --- |
| Prompt chaining | Әр қадамның нәтижесі — келесі қадамның кірісі | Explore → plan → code → commit |
| Routing | Кірісті жіктеп, дұрыс маманға жіберу | Арзан жұмысқа `model: haiku`, архитектураға Opus |
| Parallelisation | Тәуелсіз тілімдерді бір мезетте (sectioning) немесе бір тілімді бірнеше рет жасап салыстыру (voting) | `/batch`, екі worktree |
| Orchestrator-worker | Жетекші бөліністі жұмыс үстінде шешеді де, тапсырады | Төмендегі зерттеу жүйесі |
| Evaluator-optimizer | Біреуі жасайды, екіншісі сынайды, цикл қайталанады | Өз diff-іңді таза контекстегі тексеруші қарайды |

Нақты мысал — Anthropic-тің [көп агентті зерттеу жүйесі](https://www.anthropic.com/engineering/multi-agent-research-system), 2025 ж. маусым: жетекші Opus 4 agent іздеуді жоспарлайды да, қатар жұмыс істейтін Sonnet 4 subagent-терін іске қосады. Әрқайсысы өзінің таза контекст терезесінде іздейді және жетекшіге қысқартылған қорытынды қайтарады. Ішкі зерттеу бағалауында бұл жүйе жалғыз Opus 4 agent-тен 90,2% асып түсті.

Енді сол жазбаның шыншыл жартысы. Браузермен жұмыс бенчмаркінде нәтиже айырмашылығының шамамен 80%-ын тек қана token шығыны түсіндірді — архитектура негізінен көбірек token-ді, көбірек терезеде, бір уақытта жұмсағандықтан жұмыс істейді. Сол жазбада тағы айтылады: ортақ контексті талап ететін немесе тәуелділігі көп тапсырмалар бұған келмейді, ал код жазудағы жұмыстың шын мәнінде қатар жүретін бөліктері зерттеуге қарағанда әлдеқайда аз.

<Deeper title="Бар қулық — қысқаша қорытындыда, қатарластықта емес">
Anthropic-тің [контекст инженериясы туралы жазбасы](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) ұзақ мерзімді жұмысқа арналған үш тәсілді атайды: контексті сығу (compaction), терезеден тыс дискіге жазылатын жазбалар және subagent архитектурасы — тар тапсырмаға таза терезе, ал жетекшіге қысқартылған қорытынды.

Мұны сығу деп оқы. Subagent қырық файлды оқып шығып, бір абзац қайтара алады; жетекшінің терезесі сол абзац үшін ғана төлейді, қырық файл үшін емес. Кең іздеуді тапсыру асықпай отырған кезде де пайда беретіні сондықтан, ал бүкіл жазбасын түгел қайтарған subagent саған ештеңе бермегені де сондықтан. Subagent анықтамасындағы ең маңызды жол — нәтиже келісімі (output contract).
</Deeper>

## Бүгін кешке Claude Code-та мұны қалай істейсің

[Құжаттамада қатар жұмыс істеудің барлық нұсқасы бір бетке жиналған](https://code.claude.com/docs/en/agents). Міне, саған қаншалықты еркіндік беретініне қарай өсу ретімен тізілген саты:

- **Subagent-тер.** Бір сеанстың ішіндегі жұмысшылар, әрқайсысының өз контекст терезесі, құралдары және моделі бар. Анықтаманы `.claude/agents/<name>.md` файлына жаз; арзан жұмысқа `model: haiku`, файл өзгертетін болса `isolation: worktree` қой. Олар негізгі әңгімеден төмен үш қабатқа дейін тереңдейді, ал бір мезетте жиырмасы жұмыс істеп тұрса, жаңасы іске қосылмайды.
- **Worktree.** Сол repo-ның өз тармағындағы (branch) екінші жұмыс каталогы — сондықтан екі сеанс бір файлға ешқашан бірге тие алмайды. Бұл қатар жүрудің тәсілі емес, бұл — қалғандарын бір-біріне соқтықтырмайтын қабат.
- **Фондық және бұлттық сеанстар.** `claude agents` — зерттеу алдындағы алдын ала нұсқа — фондық сеанстарды бір экраннан жіберіп, бақылауға мүмкіндік береді; әрқайсысы файл өзгертер алдында өз worktree-сіне көшеді. `claude --cloud` тапсырманы Anthropic басқаратын виртуалды машинада орындайды, ол сенің тармағыңды клондайды — сондықтан алдымен push жаса; `claude --teleport` жұмысты компьютеріңе қайтарып әкеледі.
- **Agent командалары.** Жетекші және ортақ тапсырма тізімі мен пошта жәшігі бар командаластар. Тәжірибелік мүмкіндік, әдепкіде өшірулі. Үш-бес командалас, әрқайсысына бес-алты тапсырма, әр файлдың бір иесі — командаластар worktree-мен *оқшауланбайды*, сондықтан файлдарды бөлу — сенің жұмысың.
- **Динамикалық workflow-лар.** Claude скрипт жазады, оны орындау ортасы фонда жүргізеді, ал сенің контекстіңе тек соңғы жауап қайтады. Әдепкіде бір мезетте он алты agent, бір жүгірісте мыңға дейін, ал жоспарда шамамен жиырма бестен асса, ескерту шығады.

<Terminal title="bash">
```bash
# one isolated checkout per parallel task
claude --worktree signup-form
# -> .claude/worktrees/signup-form/ on branch worktree-signup-form

git worktree list          # every parallel checkout you have open

# a worktree is a fresh checkout: install deps again, and list the
# gitignored files (.env and friends) you need copied into each one
echo ".claude/worktrees/" >> .gitignore
echo ".env" >> .worktreeinclude

# push first, then hand a long job to a cloud session
claude --cloud "Execute the migration plan in docs/migration-plan.md"
```
</Terminal>

Lab 07-ге өтпей тұрып тағы біреуі: `/batch <instruction>` пәрмені бір үлкен өзгерісті worktree-мен оқшауланған бес-отыз subagent-ке бөледі, әрқайсысы өз pull request-ін ашады. Бұл — құралдағы ең жылдам заңды fan-out (жұмысты бірнеше agent-ке жаю), әрі ешкім оқымайтын отыз PR шығарудың ең жылдам жолы.

Ең қиыны — бөліністің өзі. Мына prompt ештеңе іске қосылмай тұрып, соны ашық айтуға мәжбүрлейді.

## Ақша қайда кетеді және оны қалай бақылайсың

Қатар жүрген жұмыс token шығынын еселейді; бұл — жанама әсер емес, тетіктің өзі. [Claude Code шығындары туралы құжаттамада](https://code.claude.com/docs/en/costs) agent командасы туралы былай делінген: "approximately 7x more tokens than standard sessions when teammates run in plan mode" — яғни командаластар plan mode-та жұмыс істегенде қарапайым сеанстан шамамен 7 есе көп token. Санды әрқашан осы шартымен бірге айт, өйткені бұл еселік — команданың тұрақты қасиеті емес.

1. **Модельдерді рөлге қарай тарат.** Қымбат модель жоспарлап, қорытады, арзан модель қатар жүретін қара жұмысты істейді — зерттеу жүйесіндегі Opus-жетекші, Sonnet-жұмысшылар пішіні. Қарапайым subagent-терге `model: haiku` қой; командаластарды іске қосқанда модельді атап айт.
2. **Циклге түсетін нәрсенің бәріне шек қой.** Prompt-тың ішіне итерация шегін жаз, скриптпен жүргізілетін жүгірістерге `--max-budget-usd` қос. Күтпеген шоттар дәл осы жерден — API кілтімен шексіз айналып жатқан циклдерден — шығады.
3. **`/usage` пәрменін оқы.** Ол жоспар бойынша жолақтарды және шығынның неге кеткенін көрсетеді: skill-дер, subagent-тер, плагиндер, MCP серверлері, циклдер. `/insights` сенің қалай жұмыс істейтінің туралы HTML есеп жазады; `/context` қазіргі терезені не толтырып тұрғанын көрсетеді.
4. **Қалыпты деңгейдің қандай екенін біл.** Сол шығындар беті корпоративтік қолданысты бір әзірлеушіге белсенді күніне шамамен $13 деп бағалайды, ал пайдаланушылардың 90%-ы үшін белсенді күніне $30-дан аз. Егер бір түстен кейінгі fan-out осыдан әлдеқайда асып кетсе, оның орнына атын атап айта алатын нәрсе алғаның жөн.

Бір пәрменмен емес, нағыз бақылаумен жұмыс істегісі келетін команда үшін Claude Code [OpenTelemetry-ге деректер шығарады](https://code.claude.com/docs/en/monitoring-usage): `CLAUDE_CODE_ENABLE_TELEMETRY=1` және `OTEL_EXPORTER_OTLP_ENDPOINT` қосылса, сен `claude_code.token.usage`, `claude_code.cost.usage` және `claude_code.code_edit_tool.decision` көрсеткіштерін аласың. Соңғысы — өзгерістердің қаншалықты жиі қабылданатыны — ешкім қарамайтын сан.

Нәтиже берген нәрсе — иерархия: қосалқы жоспарлаушыларды іске қоса алатын жоспарлаушылар, бір тапсырманы үнсіз тартып отыратын жұмысшылар және әр циклдің соңындағы төреші. Бір рөлді — интеграторды — алып тастау бір кедергіні жойды. Қосылған әрбір agent — үйлестірудің тағы бір беті.
</Myth>

## Ереже: тәуелсіз әрі өз алдына тексерілетін

Мұның жұмыс істейтінін көрсеткен ең үлкен жарияланған мысал — Nicholas Carlini-дің [қатар жүгірген Claude-тар құрастырған C компиляторы](https://www.anthropic.com/engineering/building-c-compiler), 2026 ж. ақпан: он алты Opus 4.6 данасы, әрқайсысы өз Docker контейнерінде, өз клонымен, әрқайсысы шексіз циклде, тапсырмаларды құлып файлдары арқылы бөліп алып отырды. Екі аптада шамамен екі мың сеанс, $20 000-нан сәл кем, үш архитектурада Linux 6.9 жүйесін компиляциялайтын шамамен 100 000 жол Rust коды.

Екі сабақ сенің ноутбугіңе дейін кішірейеді. Agent дәл тесттер анықтаған мәселені шешуге бейімделеді, сондықтан әлсіз тесттер сенімді түрде қате өнім береді — ал он алты agent сондай өнімді он алты есе көп жасайды. Екіншісі: әр agent бір алып тапсырмаға тірелген сайын қатарластық құлап отырды; емі — agent қосу емес, сол тапсырманы сырттағы эталонға (oracle) сүйеніп бөлу болды.

Осыдан осы беттегі кез келген жүйеден аман шығатын ереже туады. **Тек тәуелсіз әрі өз алдына тексерілетін жұмысты ғана қатар жүргіз.** Тәуелсіз: бөлек файлдар, ортақ дизайн шешімі жоқ. Өз алдына тексерілетін: әр тілімнің өз тексеруі бар — тест, build немесе скрипт — ол адам diff оқымай-ақ өтеді немесе құлайды. Осы екі шарттың біреуінен өтпеген жұмыс бір сеанста, кезекпен істелуі керек.

<Deeper title="Осы айда-ақ іске қоса алатын әдепкі жинақ">
Негізгі сеанста бір agent. Зерттеу жұмысына subagent-тер — файл оқулары мен журнал үйінділері басқа біреудің терезесінде қалып, саған қысқа қорытынды болып оралады. Өзің жазбаған әр diff-ке таза контекстегі тексеруші — екі қатысушысы бар evaluator-optimizer.

Қатар *жазатын* agent-терді тексеру тізімі өткенде ғана қос, worktree-лермен және әр файлға бір иеден. Agent командалары мен отыз subagent-тен тұратын batch — шын бар нәрсе; бірақ оларға бірінші емес, ең соңғы кезекте қол созасың.
</Deeper>
