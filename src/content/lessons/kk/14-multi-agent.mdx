Anthropic-тің зерттеу жүйесінде жетекші agent жұмысты subagent-терге таратады. Ішкі бағалауда ол жалғыз agent-тен айтарлықтай озады, әрі кәдімгі чаттан шамамен он бес есе көп token жейді. Көп agent — *тегін жылдамдық* емес. Бұл — айырбас.
</Lead>

Осы уақытқа дейін жасағаныңның бәрі бір agent, бір сеанс, бір терминалмен бітті. Жұмыстың көбіне дұрыс пішін әлі де сол. Бұл модуль — ерекше жағдайлар туралы.

## Бес пішін және Anthropic шынымен шығарғаны

Терминдер Erik Schluntz пен Barry Zhang жазған [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) мақаласынан алынды, 2024 ж. желтоқсан. Бес үлгі, үшеуін сен қолданып та қойдың. Кеңесі уақыт сынынан өтті: қарапайымнан баста, күрделілікті нәтижені өлшеуге болатындай жақсартқанда ғана қос.

| Пішін | Не екені | Қай жерде кездестірдің |
| --- | --- | --- |
| Prompt chaining | Әр қадамның нәтижесі — келесі қадамның кірісі | Explore → plan → code → commit |
| Routing | Кірісті жіктеп, дұрыс маманға жіберу | Арзан жұмысқа `model: haiku`, архитектураға Opus |
| Parallelisation | Тәуелсіз тілімдерді бір мезетте (sectioning) немесе бір тілімді бірнеше рет жасап салыстыру (voting) | `/batch`, екі worktree |
| Orchestrator-worker | Жетекші бөліністі жұмыс үстінде шешеді де, тапсырады | Төмендегі зерттеу жүйесі |
| Evaluator-optimizer | Біреуі жасайды, екіншісі сынайды, цикл қайталанады | Өз diff-іңді таза контекстегі тексеруші қарайды |

Нақты мысал — Anthropic-тің [көп агентті зерттеу жүйесі](https://www.anthropic.com/engineering/multi-agent-research-system), 2025 ж. маусым: жетекші Opus 4 agent іздеуді жоспарлайды да, қатар жүретін Sonnet 4 subagent-терін іске қосады. Әрқайсысы өз таза терезесінде іздеп, жетекшіге қысқартылған қорытынды қайтарады. Ішкі зерттеу бағалауында ол жалғыз Opus 4-тен 90,2% асып түсті.

Енді сол жазбаның шыншыл жартысы. Браузер бенчмаркінде нәтиже айырмашылығының шамамен 80%-ын тек token шығыны түсіндірді — жүйе негізінен көбірек token-ді, көбірек терезеде, бір уақытта жұмсағандықтан жұмыс істейді. Ортақ контексті талап ететін немесе тәуелділігі көп тапсырмалар бұған келмейді, ал кодта қатар жүретін бөлік зерттеудегіден аз.

## Бүгін кешке Claude Code-та мұны қалай істейсің

[Құжаттамада қатар жұмыс істеудің барлық нұсқасы бір бетте](https://code.claude.com/docs/en/agents), саған қаншалықты еркіндік беретініне қарай өсу ретімен:

- **Subagent-тер.** Бір сеанс ішіндегі жұмысшылар, әрқайсысының өз контекст терезесі, құралдары және моделі бар. Анықтаманы `.claude/agents/<name>.md` файлына жаз; арзан жұмысқа `model: haiku`, файл өзгертетін болса `isolation: worktree` қой. Негізгі әңгімеден төмен үш қабатқа дейін тереңдейді, ал бір мезетте жиырмасы жүрсе, жаңасы қосылмайды.
- **Worktree.** Сол repo-ның бөлек тармағындағы (branch) екінші жұмыс каталогы ([09-модуль](/kk/learn/git-and-github/)), сондықтан екі сеанс бір файлға бірге тие алмайды. Бұл қатар жүрудің тәсілі емес — соқтығысты болдырмайтын қабат.
- **Фондық және бұлттық сеанстар.** `claude agents` — зерттеу алдындағы нұсқа — фондық сеанстарды бір экраннан жіберіп, бақылайды; әрқайсысы файл өзгертер алдында өз worktree-сіне көшеді. `claude --cloud` тапсырманы Anthropic басқаратын виртуалды машинада орындайды, ол тармағыңды клондайды — алдымен push жаса; `claude --teleport` жұмысты кері әкеледі.
- **Agent командалары.** Жетекші және ортақ тапсырма тізімі мен пошта жәшігі бар командаластар. Тәжірибелік, әдепкіде өшірулі. Үш-бес командалас, әрқайсысына бес-алты тапсырма, әр файлдың бір иесі. Командаластар worktree-мен *оқшауланбайды*, сондықтан файлдарды бөлу — сенің жұмысың.
- **Динамикалық workflow-лар.** Claude скрипт жазады, оны орындау ортасы фонда жүргізеді, ал контекстіңе тек соңғы жауап қайтады. Әдепкіде бір мезетте он алты agent, бір жүгірісте мыңға дейін, жоспар шамамен жиырма бестен асса — ескерту.

<Terminal title="bash">
```bash
# one isolated checkout per parallel task
claude --worktree signup-form
# -> .claude/worktrees/signup-form/ on branch worktree-signup-form

git worktree list          # every parallel checkout you have open

# a worktree is a fresh checkout: install deps again, and list the
# gitignored files (.env and friends) you need copied into each one
echo ".claude/worktrees/" >> .gitignore
echo ".env" >> .worktreeinclude

# push first, then hand a long job to a cloud session
claude --cloud "Execute the migration plan in docs/migration-plan.md"
```
</Terminal>

## Ақша қайда кетеді және оны қалай бақылайсың

[Claude Code шығындары туралы құжаттамада](https://code.claude.com/docs/en/costs) agent командасы туралы былай делінген: "approximately 7x more tokens than standard sessions when teammates run in plan mode" — яғни командаластар plan mode-та жүргенде қарапайым сеанстан шамамен 7 есе көп token. Санды осы шартымен бірге айт: еселік тұрақты емес.

1. **Модельдерді рөлге қарай тарат.** Қымбат модель жоспарлап, қорытады, арзан модель қара жұмысты істейді — зерттеу жүйесіндегі Opus-жетекші, Sonnet-жұмысшылар пішіні. Қарапайым subagent-терге `model: haiku` қой; командаластарды қосқанда модельді атап айт.
2. **Циклге түсетін нәрсенің бәріне шек қой.** Prompt ішіне итерация шегін жаз, скриптпен жүргізілетін жүгірістерге `--max-budget-usd` қос. Күтпеген шоттар осы жерден шығады: API кілтімен шексіз айналған циклдерден.
3. **`/usage` пәрменін оқы.** Жоспар жолақтары және шығын неге кеткені: skill-дер, subagent-тер, плагиндер, MCP серверлері, циклдер. `/insights` жұмыс тәртібің туралы HTML есеп жазады; `/context` қазіргі терезені не толтырып тұрғанын көрсетеді.
4. **Қалыпты деңгейді біл.** Сол бет корпоративтік қолданысты бір әзірлеушіге белсенді күніне шамамен $13 деп бағалайды, ал пайдаланушылардың 90%-ы үшін белсенді күніне $30-дан аз. Түстен кейінгі fan-out осыдан әлдеқайда асса, орнына атын атай алатын нәрсе алғаның жөн.

Нағыз бақылау керек болса, Claude Code [OpenTelemetry-ге деректер шығарады](https://code.claude.com/docs/en/monitoring-usage): `CLAUDE_CODE_ENABLE_TELEMETRY=1` және `OTEL_EXPORTER_OTLP_ENDPOINT` қосылса, `claude_code.token.usage`, `claude_code.cost.usage` және `claude_code.code_edit_tool.decision` көрсеткіштерін аласың. Соңғысы — өзгерістердің қаншалықты жиі қабылданатыны — ешкім қарамайтын сан.

Cursor мұны сынап көрді. Бір-біріне тең жиырма agent құлыптар арқылы келісіп жұмыс істегенде, өнімділік екі-үш agent деңгейіне құлады: құлыптар тым ұзақ ұсталды немесе мүлде босатылмады. Оптимистік қатарластық басқаша сәтсіздікке ұшырады — agent-тер тәуекелден қашып, ұсақ әрі қауіпсіз өзгерістер жасап, орнында тапталды.

Нәтиже бергені — иерархия: қосалқы жоспарлаушыларды қоса алатын жоспарлаушылар, бір тапсырманы үнсіз тартатын жұмысшылар, әр циклдің соңында төреші. Интегратор рөлін алып тастау бір кедергіні жойды. Қосылған әрбір agent — үйлестірудің тағы бір беті.
</Myth>

## Ереже: тәуелсіз әрі өз алдына тексерілетін

Ең үлкен жарияланған мысал — Nicholas Carlini-дің [қатар жүгірген Claude-тар құрастырған C компиляторы](https://www.anthropic.com/engineering/building-c-compiler), 2026 ж. ақпан: он алты Opus 4.6 данасы, әрқайсысы өз Docker контейнерінде, өз клонымен, шексіз циклде, тапсырмаларды құлып файлдары арқылы бөліп алды. Екі аптада шамамен екі мың сеанс, $20 000-нан сәл кем, үш архитектурада Linux 6.9 жүйесін компиляциялайтын шамамен 100 000 жол Rust коды.

Ноутбугіңе қатысты екі сабақ. Agent дәл тесттер анықтаған мәселені шешуге бейімделеді, сондықтан әлсіз тесттер сенімді түрде қате өнім береді ([10-модуль](/kk/learn/test-and-quality/)) — ал он алты agent соны он алты есе көп жасайды. Екіншісі: әр agent бір алып тапсырмаға тірелген сайын қатарластық құлап отырды; емі — agent қосу емес, сол тапсырманы сырттағы эталонға (oracle) сүйеніп бөлу.

**Тек тәуелсіз әрі өз алдына тексерілетін жұмысты ғана қатар жүргіз.** Тәуелсіз: бөлек файлдар, ортақ дизайн шешімі жоқ. Өз алдына тексерілетін: әр тілімнің өз тексеруі бар — тест, build немесе скрипт — ол адам diff оқымай-ақ өтеді немесе құлайды. Осы екеуінің біреуінен өтпеген жұмыс бір сеанста, кезекпен істеледі.

<Deeper title="Осы айда-ақ іске қоса алатын әдепкі жинақ">
Негізгі сеанста бір agent. Зерттеуге subagent-тер — файл оқулары мен журнал үйінділері саған қысқа қорытынды болып оралады. Өзің жазбаған әр diff-ке таза контекстегі тексеруші.

Қатар *жазатын* agent-терді тексеру тізімі өткенде ғана қос: worktree-лермен, әр файлға бір иеден. Agent командалары мен отыз subagent-тік batch — ең соңғы кезекте қол созатын нәрсе.
</Deeper>
