<Lead>
Агент кодты сен оқып үлгергеннен де жылдам өзгертеді. Мәселе ешқашан оның қателесу-қателеспеуінде болған емес. Мәселе — сол қате саған қаншаға түсетінінде. git бар болса, жауабы — *бір пәрмен*.
</Lead>

Нұсқаларды басқару жүйесі жоқ болса, агентті іске қосқан сайын артқа жол жабылады. Сонда машинамен «үш промпт бұрын нені өзгерттің» деп таласып отырасың да, жұмыс істеп тұрған нұсқадан ақырындап айырыласың. Жүйе бар болса, сәтсіз әрекет уайымға тұрмайды: тастай сал, промптты жақсырақ жаз, қайта іске қос. Алда тұрған батыл істің бәрі — ұзақ жұмыстар, тәуекелді рефакторинг, агентті дерекқор қабатына жақын жіберу — тек кері қайта алатының үшін ғана ақылға қонады.

## Бүкіл жүйені бес сөз ұстап тұр

| Сөз | Не екені | Қалай елестету керек |
|---|---|---|
| **Репозиторий (repo)** | Жобаңның қалтасы және оның толық тарихы — бәрі жасырын `.git` қалтасында жатады. Интернетсіз де жұмыс істейді, аккаунт та қажет емес. | Әр беттің барлық бұрынғы нұсқасы тігілген қалың бума |
| **Commit** | Бір сақталған түсірілім: файлдардың дәл сол сәттегі күйі және өзгерісті түсіндіретін хабар. | Суреті қоса тіркелген күнделік жазбасы |
| **Тармақ (branch)** | Жұмыстың қатар жүретін желісі. Сонда жұмыс істей бер, ал `main` сен біріктіргенге дейін бұрынғы қалпында қала береді. | Үстіне сызғылау үшін негізгі құжаттың көшірмесін алу |
| **Remote** | Репозиторийдің серверде тұрған көшірмесі — әдетте GitHub. Оған push жасайсың, одан pull жасайсың. | Үйден тыс жердегі банк сейфі |
| **Pull request** | Бір тармақты екіншісіне біріктіру туралы ұсыныс. Қай жолдар өзгергенін дәл көрсетеді және алдымен тексерулерді жүргізеді. | Баспаға кетер алдында қолжазбаны редакторға беру |

Керекті сөздік осы. Күнделікті жұмыстың дені бес пәрменге сияды.

<Terminal title="bash">
```bash
cd qairu-signup
git init
git status
git add .
git commit -m "chore: first working version"
git log --oneline
```
</Terminal>

Ең жиі орындайтын пәрменің — `git status`. Ол «соңғы түсірілімнен бері не өзгерді және келесісіне не кіргелі тұр» деген сұраққа жауап береді. `git add` сол түсірілімге кіретін файлдарды дайындап қояды, `git commit` түсірілімнің өзін жасайды, ал `git log --oneline` тарихты әр commit-ке бір жол бөліп оқып береді.

## Ноутбуктағы қалтадан интернеттегі мекенжайға дейін

GitHub-та бос репозиторий жаса (README де, лицензия да керек емес — файлдарың бұрыннан бар), ол көрсеткен URL-ді көшіріп ал да, екеуін байланыстыр.

<Terminal title="bash">
```bash
git remote add origin https://github.com/YOUR-NAME/qairu-signup.git
git branch -M main
git push -u origin main
```
</Terminal>

Алғашқы push-тан кейін жай ғана `git push` жетеді. Кері бағыты — `git pull`: ол қашықтағы репозиторийде бар, ал сенде жоқ commit-терді алып түседі. Бұл — басқа ноутбукта істеген жұмысың немесе сен ұйықтап жатқанда әріптесің біріктірген өзгеріс. Оны жұмысты бастар алдында орында, сол файлды өзгертіп қойғаннан кейін емес. Енді тарихың екі жерде тұр, ал кейінгі модульдерде хостингті сол URL-ге бағыттап, әр push сайын deploy жасатуға болады.

## .gitignore — ноутбугыңнан ешқашан шықпауға тиіс нәрселердің тізімі

`.gitignore` файлы git-ке қай жолдарды көрмегенсуі керегін айтады. Кәдімгі жобаға төрт жол жетеді:

<Terminal title=".gitignore">
```text
.env
node_modules/
dist/
.claude/worktrees/
```
</Terminal>

`.env` ішінде API кілттерің жатыр — орта айнымалыларының бүкіл мәні құпия деректерді репозиторийден тыс ұстауда. `node_modules/` қайта орнатылады әрі орасан үлкен, `dist/` автоматты түрде жасалады, ал `.claude/worktrees/` — қатар екі сеанс ашқанда Claude Code қатарлас жұмыс көшірмелерін қоятын жер.

<Callout type="danger" title="Commit-ке түскен құпия дерек кері шықпайды">
Кілтті файлдан өшіріп, қайта commit жасау оны жойып жібермейді. Бұрынғы әр түсірілімде ол әлі тұр, ал push жасап қойған болсаң — бөтен адамның серверінде де тұр. Кілт бір рет commit-ке түссе, оны жария деп есепте: жаңа кілт ал да, ескісінің күшін жой. `.gitignore` файлын бірінші commit-тен бұрын жаз, кейін емес.
</Callout>

## Түнгі екіде де оқи алатын commit хабарларын жаз

Commit хабарының бір ғана міндеті бар: болашақтағы оқырман — сен, әріптесің немесе жаңа сеанстағы агент — екі секундта «кері қайтарғым келген commit осы ма» дегенді шеше алсын. Conventional commits стилі мұны автоматты түрде шешеді: тип, қажет болса scope, содан соң бір жол қарапайым сипаттама.

<Terminal title="git log --oneline" copy={false}>
```text
feat(signup): store reservations in D1
fix(form): reject an empty email instead of saving it
test(form): cover the duplicate-email case
refactor(api): split the handler into two files
docs(readme): how to run the dev server
chore(deps): bump astro
```
</Terminal>

Алты тип күнделікті жағдайдың бәрін дерлік қамтиды: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`. Бірінші жолды тізімде көзбен шолып өтерліктей қысқа ұста, ал *неге* екенін керек болса хабардың негізгі бөлігіне жаз. Пайдасы мынада: `git log --oneline` жолма-жол кері қайтара алатын өзгерістер журналына айналады. Anthropic-тің [ұзақ жұмыс істейтін агенттердің жұмыс ортасы туралы мақаласы](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) дәл осы әдетке агент жағынан келеді: әр аяқталған жұмыс бөлігінен кейін өзгерісті сипаттайтын хабармен commit жасатып отыр — сонда кейінгі сеанс жұмыс істеген күйге жолын таба алады.

## Кері қайтарудың үш түрі бар, push-тан кейін қауіпсізі — біреуі ғана

Мынаны шынымен жаттап алған жөн. Жағдайға сәйкес пәрменді тап.

| Не болды | Нені орындайсың |
|---|---|
| Агент файлдарды өзгертті, ештеңе commit-ке түспеген, ескі күйді қайтарғың келеді | Бақылаудағы файлдар үшін `git restore .` |
| Оның үстіне керексіз жаңа файлдар жасап тастады | `git clean -fd` — бақылауда жоқ файлдар мен қалталарды жояды |
| Былықты жоғалтпай, уақытша бір шетке қойғың келеді | `git stash`, кері әкелу үшін `git stash pop` |
| Соңғы commit нашар шықты, ал сен оны push жасаған **жоқсың** | `git reset --hard HEAD~1` — commit жойылады |
| Нашар commit push жасалып немесе басқаларға таралып кеткен | `git revert HEAD` — жаңа commit оны кері қайтарады |

`git clean -fd` бақылауда жоқ файлдарды біржола жояды — git оларды ешқашан жазып алмаған, сондықтан қалпына келтіретін ештеңе жоқ. `-x` қоспасаң, елемеу тізіміндегі файлдар аман қалады, демек `.env` файлың қауіпсіз. Алдымен `git clean -nd` пәрменін орында: `-n` ештеңеге тимей, нені жоятынын тізіп береді.

<Compare a="git reset --hard" b="git revert">
<div slot="a">
Тармақты артқа шегіндіріп, commit-ті жояды. Жұмыс әлі тек ноутбугыңда тұрғанда — тамаша. Ал push жасалғаннан кейін бұл — тұзақ: сенің тарихың мен қашықтағы репозиторийдің тарихы қайшы келеді, келесі push `--force` талап етеді, ал басқалар pull жасап үлгерген тармақты күшпен басып жазу — бүкіл топтың еңбегі жоғалатын жағдайдың дәл өзі.
</div>
<div slot="b">
Нашар commit-тің дәл кері көшірмесі болатын жаңа commit қосады. Ештеңе жойылмайды, ештеңе қайта жазылмайды, ал журнал қатені де, оның кері қайтарылуын да адал көрсетіп тұрады. Бұл push-қа дейін де, одан кейін де қауіпсіз. Әдепкі таңдауың осы.
</div>
</Compare>

Revert тек соңғы commit-пен ғана емес, кез келгенімен жұмыс істейді: `git log --oneline` шығарып оқы, қысқа hash-ты көшір де, `git revert a1b2c3d` пәрменін орында. Егер оның үстіне кейінгі жұмыс салынған болса, git болжап отырмайды: тоқтайды да, қайшылықты көрсетеді.

## Checkpoint — жергілікті кері қайтару. Git — тұрақты кері қайтару.

Claude Code-тың өз сақтандыру торы бар. Кезекті бастайтын әр промпт checkpoint жасайды, ал файлдар әр өңдеуден бұрын түсіріліп алынады; бос енгізу жолында `Esc Esc` басу немесе `/rewind` пәрмені кодты да, әңгімені де — не соның біреуін ғана — қалпына келтіретін мәзір ашады. «Соңғы өңдеу қате болды» деген жағдайда ол кез келген git пәрменінен озады.

Бірақ бұл git-тің орнын баспайды — [checkpoint құжаттамасының](https://code.claude.com/docs/en/checkpointing) өзі солай дейді. Әр сеанста тек соңғы 100 checkpoint сақталады, ал сеанс соңғысын сақтағаннан кейін шамамен 30 күн өтсе, олар тазаланады. Одан да маңыздысы: олар `rm`, `mv`, `cp` секілді Bash пәрмендері жасаған өзгерістерді, субагенттердің өңдеулерінің көпшілігін, сеанстан тыс енгізілген түзетулерді, символдық және қатты сілтемедегі файлдарды бақыламайды.

<Callout type="warn" title="Ең қатерлі жағдай — дәл қамтылмағаны">
Ең көп зиян келтіретіні — агент терминалға шығып кеткен жағдай: қалтаны көшіріп жібереді, каталогты жояды, файлдарды скриптпен қайта жасайды. Checkpoint қамтымайтын санат дәл осы. Ал commit бәрін қамтиды, өйткені commit файлды кім, қалай өзгерткеніне қарамайды.
</Callout>

## Enter пернесін баспай тұрып commit жаса

Осы беттен алып кететін ереже мынау: **бірден көп файлға тиетін промпт жібермес бұрын `git status` «working tree clean» деп тұруға тиіс.** Содан кейін өз тексерісінен өткен әр жұмыс бөлігін келесісін бастамай тұрып commit жаса.

Екі себебі бар, екеуі де қағазбастылық емес.

Біріншіден: мақұлдаудан шаршау — теория емес, өлшенген дүние. Әр сұрауға дерлік «иә» десең, «рұқсат беру» түймесін басу шешім болудан қалады. Ал Claude Code-тың auto mode режимі сенің атыңнан «иә» дейтін классификаторға сүйенеді, ал ол шынымен шектен шыққан әрекеттердің 17%-ын әлі де өткізіп жібереді. Екі қабаттың бірі де қабырға емес. Агентті іске қоспай тұрып жасалған commit — ешқашан шаршамайтын жалғыз қорғаныс шегі.

Екіншіден: шағын commit-тер бақылауды арзандатады. Қырық жолдық diff-ті шынымен оқып шығасың. Екі мың жолдық diff-ті сырғытып өтіп, мақұлдай саласың — бұл тексеру емес, жай ғана қол қою.

<Prompt title="Агентіңе арналған git ережелері" where="Claude Code · AGENTS.md or the first message of a session">
```text
Осы репозиторийдің git ережелері:
- Тапсырманы бастамас бұрын `git status` орында. Жұмыс каталогы таза болмаса, тоқта да, маған айт.
- feat/<қысқа-атау> немесе fix/<қысқа-атау> деп аталған тармақта жұмыс істе.
  main тармағына ешқашан тікелей commit жасама.
- Өз тексерісінен өткен әр жұмыс бөлігінен кейін commit жаса. Бір commit — бір логикалық өзгеріс.
- Хабар пішімі: type(scope): не өзгергені.
  Типтері: feat, fix, docs, refactor, test, chore.
- `git push --force` ешқашан орындама. Push жасалып қойған commit-ке ешқашан amend жасама.
  .env файлын да, .gitignore тізіміндегі ештеңені де ешқашан қоспа.
- Тапсырма біткенде маған осы тармақтың `git log --oneline` тізімін және main-ге қатысты
  `git diff --stat` нәтижесін көрсет, содан соң pull request ашпай тұрып, менің тексеруімді күт.
```
</Prompt>

## Әр тапсырмаға бір тармақ, әр тексеруге бір pull request

Тармақты агент жұмысты бастағаннан кейін емес, бұрын жаса: `git checkout -b feat/seat-counter`. Іс сәтсіз біткенде тармақты өшіресің де, `main` ештеңе білмей қала береді. Сәтті біткенде pull request аш — иә, жалғыз өзің істесең де, жобаңды ешкім көрмейтін болса да. Diff-ті файлдап оқитын жерің де, автоматты тексерулер жүретін жер де, өзі жазбаған кодты жаңа агент сеансы қарап шыға алатын жер де — сол.

Simon Willison-ның агенттік анти-паттерндер жинағы осы жердегі ең маңыздысын атайды: өзің оқып шықпаған код бар pull request ашпа; оларды шағын ұста әрі жұмыс істейтінінің дәлелін қоса тіркеп жібер. [Анти-паттерндер](https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/) және оның [кодтайтын агенттермен git-ті қолдану](https://simonwillison.net/guides/agentic-engineering-patterns/using-git-with-coding-agents/) туралы тарауы — осы беттен кейін оқитын дүние.

<Myth
  n={9}
  myth="Агенттер мұншама жақсы болған соң, кодты түсінудің қажеті қалмады."
  source="Simon Willison · anti-patterns"
  href="https://simonwillison.net/guides/agentic-engineering-patterns/anti-patterns/"
>
Оқи алмайтын нәрсеңді қалпына келтіре де алмайсың. Осы беттегі әр қимыл бағалаудан басталады: қай өзгеріс тапсырманың бөлігі еді, қатені қай commit әкелді, мына diff — түзету ме, әлде екінші қате ме. Willison-ның анти-паттерндер тізімі pull request туралы дәл осы ережені айтады — өзің оқып шықпаған код бар pull request ашпа — ал мұндағы кері қайтарудың бәрі сол қабілетке сүйенеді. Git саған дәлел береді; оны оқу — әлі де сенің ісің. Сен түсінбейтін код жазатын агент жұмысты жойған жоқ — ол оны ең жаман сәтке, бірдеңе бұзылып қойған сәтке жылжытты.
</Myth>

<Deeper title="Қатар екі агент қосқанда: әрқайсысына бір worktree">
Worktree — өз тармағында тұратын, бірақ сол репозиторийдің тарихын бөлісетін екінші жұмыс каталогы. Сондықтан екі агент сеансы бір-бірінің файлдарын ешқашан басып жазбайды. Қолмен: `git worktree add ../qairu-feature-a -b feature-a`, оған қоса `git worktree list` және `git worktree remove`. Claude Code мұны `claude --worktree feature-auth` деген бір пәрменге сыйдырған: ол `worktree-feature-auth` деген тармақта `.claude/worktrees/feature-auth/` каталогын жасайды және шыққанда таза worktree-лерді өшіреді. Бұл — жаңадан жасалған көшірме, сондықтан тәуелділіктерді қайта орнатасың, ал `.env` секілді елемеу тізіміндегі файлдар онымен бірге көшпейді ([worktree құжаттамасы](https://code.claude.com/docs/en/worktrees)). Мұны бірінші күні емес, екі сеанс бір-біріне соғылған алғашқы сәтте қолға ал.
</Deeper>

<Prompt title="Агент жолдан шығып кеткенде" where="Claude Code · before you undo anything">
```text
Тоқта. Енді бірде-бір файлды өзгертпе.

1. `git status` және `git diff --stat` орында да, шыққан нәтижені сол күйінде көрсет.
2. Өзгерген әр файл туралы бір жолмен айт: ол мен сұраған тапсырманың бөлігі ме,
   әлде сен өз бетіңмен өзгертуді шешкен нәрсе ме.
3. Commit жасама, git checkout, git restore, git reset, git clean пәрмендерін де орындама.
   Нені лақтырып тастайтынын мен шешемін.
```
</Prompt>

<Callout type="live" title="Мынаны сахнада көрсет">
Керексіз бір commit жаса да, залдың көз алдында `git reset --hard HEAD~1` орында, сосын `git log` ішінде ол commit жай ғана жоқ болып кеткенін көрсет. Содан соң тағы біреуін жасап, `git revert HEAD` орында да, журналда екі жазба да тұрғанын көрсет. «Жойылды» мен «кері қайтарылды» арасындағы көзге көрінетін айырма — адамдарды агентті келесі рет іске қосар алдында commit жасауға көндіретін нәрсе.
</Callout>

<ProjectStep n={9} title="QAIRU Event Sign-up жобасын git-ке сал да, әдейі бұз">
Бес қимыл. Алғашқы үшеуі репозиторийді дайындайды. Соңғы екеуін курстың қалған бөлігінде қайта-қайта істейтін боласың.

1. Жоба қалтасында: `git init`. 8-модульде жазған `.gitignore` файлыңды аш та, `.env` пен `node_modules/` қатарына `dist/` және `.claude/worktrees/` қос — бәрінен бұрын осыны істе.
2. `git add .`, содан соң `git commit -m "chore: first working version"`. Тексер: `git status` таза дейді, `git log --oneline` бір жол көрсетеді.
3. GitHub-та бос репозиторий жаса, сосын ол берген URL-мен `git remote add origin`, одан кейін `git branch -M main` және `git push -u origin main`. Бетті жаңарт — енді жобаңның мекенжайы бар.
4. Жаттығу. `git checkout -b feat/seat-counter` орында, содан соң агентіңнен тіркелу бетіне «12 орын қалды» дейтін есептегіш қосуын сұра. Аяқтасын, сосын `git add .` және `git commit -m "feat(signup): seats-left counter"`.
5. Енді оны кері қайтар: `git revert HEAD`. Бетті қайта жүкте — есептегіш жоқ, ал `git log --oneline` өзгерісті де, оның кері қайтарылуын да көрсетіп тұр. `git checkout main` пәрменімен аяқта. Жұмыс істеп тұрған нұсқаң ешқашан қауіпте болған жоқ, ал сен енді жаман күні керек болатын дәл сол қимылды жаттап алдың.
</ProjectStep>
